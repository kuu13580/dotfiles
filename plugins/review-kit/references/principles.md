# レビューの原則

review-kit の全スキルが共有する原則。流れは **洗い出す → 検証する → 3軸で議論する → 決める**。どこから始めるか (洗い出しからか、受けた指摘の検証からか) と、決めたあと何をするかはスキルごとに違う。self-review と review-response は決めたとおりに直す。pr-review は他人のコードなので、結論を指摘の重さ (必須 / 任意 / 別 PR でよい) として文面に出す。

## 1. 観点

### 基本の3軸 (固定)

| 軸 | 問い | 見るもの | 洗い出しの担当 |
| --- | --- | --- | --- |
| 正しさ | 動くか | 不具合全般 | ビルトイン `/code-review` |
| 仕様・使う人 | 求められたものか | 妥当性 / 要件担保 / エッジ / アーキ (下記) | サブエージェント |
| 保守・構造 | 保てるか | 既存ヘルパーの再利用 / 簡素化 / 効率 / 根本原因の深さ / 規約 | サブエージェント |

- `/code-review` は Skill ツールで `code-review` を呼ぶ。引数は `<level> [<対象>]`。level を省くと前回のレベルを引き継ぐので必ず明示する。`--comment` (GitHub へ直接投稿) と `--fix` (コードを書き換える) は付けない。投稿と修正は議論のあとにスキル側で行う
- 差分の大半が指示文や設定 (SKILL.md・プロンプト・設定ファイル) のときは `/code-review` が効きにくいので、正しさの担当をサブエージェントで立て、指示どうしの矛盾・分岐の漏れ・失敗したときの扱いを見させる
- `/code-review` が返す整理系の指摘 (reuse / simplification / efficiency / altitude) は保守・構造の軸の候補に合流させる
- 仕様・使う人の4観点:
  - 妥当性: コードから読める仕様を、事業・運用・アーキテクチャの観点で決めてよいのか (例: 副作用のある操作の自動リトライ、契約で変わる類の値のハードコード)
  - 要件担保: 依頼・仕様書・PR の説明に書かれた要件のうち、壊れたら影響が大きいものが実装で閉じているか
  - エッジ: 仕様にも実装にも扱いが現れていない入力・状態 (空 / 0件 / 1件 / 上限超過 / 境界値 / 同時実行 / 権限なし / 通信断 / 途中失敗)
  - アーキ: 責務の置き場所、既存の抽象との重複、依存の向き、状態の持ち方、次に似た機能が来たときに破綻しないか
- 根本原因の深さ: 共有基盤に特例を重ねる修正は浅い修正のサイン。仕組み側の一般的な修正で直せないかを見る

### 追加観点

差分のファイル種別・パス・内容で自動で足し、呼び出し時の引数 (`+<観点>`) でも足せる。追加観点で出た指摘も、議論は3軸で行う (破壊的な挙動を除く)。

| 観点 | 自動で足す条件 | 引数 | 洗い出し |
| --- | --- | --- | --- |
| セキュリティ | 認証・認可・トークン・暗号・外部入力のパース・SQL / HTML / シェルの組み立てに触れる | `+security` | 対象が今のブランチの変更ならビルトイン `/security-review`、それ以外はサブエージェント |
| 既存動作の変更 | 公開 API・設定の既定値・保存や通信の形式・既存の分岐を削除・変更している | `+behavior` | 変わる前後の挙動と、影響を受ける呼び出し元 |
| UI | `*.html` `*.tsx` `*.jsx` `*.vue` `*.svelte` `*.css` `*.scss`、`components/` `pages/` `views/` 配下 | `+ui` | `ui-principles` skill を読ませたサブエージェント (skill が無ければ省く) |
| データ移行 | `migrations/`、スキーマ定義、`*.sql`、保存データの型 | `+migration` | 既存データでの移行の成否、途中失敗、戻し方 |
| テスト | プロダクションコードを変えたのに対応するテストの変更が無い、またはテストを変えている | `+test` | 変えた分岐がテストされているか、setup / teardown の対称、実装をなぞるだけのテストになっていないか |
| 失敗・再実行 | 外部 API・git・ファイルの書き換えを伴う処理や、状態を持つ手順に触れる | `+failure` | 途中で失敗したときに残る状態、再実行・再開で二重に起きないか、取得の上限での打ち切り、前提 (ブランチ・作業ツリー・ホスト) の取り違え |
| 破壊的な挙動 | 保存・削除・同期・送信・決済・権限に触れる | `+destructive` | 下記 |

**破壊的な挙動** は、仕様どおりでも意図を確かめておきたい挙動を拾う。不具合ではないので議論にかけず、self-review・review-response では報告の「判断してください」に、pr-review では【確認】に出す。どちらも3件まで。対象は、この差分で新しく入った・条件が変わった挙動のうち、ユーザーの明示的な操作なしに次のどれかを起こすものだけ:

- 保存済みのデータを上書き・削除する (同期・マージ・不整合の解消・掃除処理・移行)
- 外部に送る・お金が動く (通知・メール・決済・外部 API への書き込み)
- 権限や公開範囲を広げる

確認ダイアログ付きの削除ボタンのように、ユーザーが操作して起こすものは対象外。

## 2. 洗い出す

- 全候補に **「具体的な入力・状態 → 誤った結果」** を付ける。整理系は代わりに具体的なコスト (何が重複・無駄・保守しづらいか) を付ける
- 半信半疑の候補も洗い出しでは落とさない。洗い出しで黙って落とすことが見逃しの主因になる。絞るのは検証の仕事
- 場所はリポジトリ相対の `path:line` で書く
- 規約違反は保守・構造の担当が見る。規約ファイル (CLAUDE.md・`.claude/rules/`・lint 設定・規約文書。変更ファイルの祖先ディレクトリにあるものを含む) を開き、**規約の原文と違反行を引用できたものだけ** 挙げる。lint が拾うもの、lint 無効化コメントで明示的に黙らせているもの、変更していない行は挙げない

## 3. 検証する

### 確度

| 確度 | 条件 | 書くこと |
| --- | --- | --- |
| 高 | 検証済み。テストで再現した、またはコードで到達経路 (呼び出し元・分岐・型) を確定した。整理系はコストを行で示せた (再利用すべき既存ヘルパーの `path:line`、重複している箇所、消せる処理) | 引き金になる入力・状態と誤った結果、根拠の行 |
| 中 | 可能性あり。仕組みは実在するが、きっかけ (タイミング・環境・設定・実機での挙動) が不確か | 何が分かれば確定するか |
| 取り下げ | コードから否定できた。事実誤認 / 型・定数・不変条件で起こり得ない / この差分内で手当て済み / 観測できる影響のない好み | 否定する行の引用 |

- 「推測だから」「実行時の状態次第」を理由に取り下げない。並行実行の競合、まれだが到達しうる null (エラー処理・コールドキャッシュ・任意項目の欠落)、境界の off-by-one、リトライの嵐・部分失敗、アンカーを失った正規表現は中
- 否定する行を引用できないものは取り下げにせず中に置く
- 規約違反は、引用した原文と違反行がそのまま根拠になるので高
- 仕様・使う人の軸で「実装者やユーザーに聞かないと決まらないこと」は、検証しても確度が上がらない。中として扱い、何を聞けば決まるかを書く

### 検証の手段 (上から順に試す)

1. **テストで再現する。** 対象の隣に、後で自分が消せると分かる名前 (`<name>.review-check.spec.ts` など) で書き、そのファイルだけを実行する。テストランナーはリポジトリの設定 (`package.json` の scripts、`vitest.config.*` / `jest.config.*` / `karma.conf.*` など) から決める。結果を控えたら自分が作ったファイルだけ消す。ただし修正まで行うスキル (self-review・review-response) では、直したあとに同じテストで直ったことを確かめてから消す。依存が入っておらず動かないときは、黙ってインストールせず判断を仰ぐ
2. **コードを追って到達経路を確定する。** 呼び出し元・型定義・分岐を実際に読む
3. **動かして確かめる。** 1・2 で中に残ったもののうち、影響が major 以上のものだけが対象 (費用がかかるため)
   - UI: 開発サーバーを立て、Playwright などリポジトリにある仕組みで問題の操作を再現する。API の応答はモック (Playwright の route、リポジトリのモックの仕組み) で差し替えてよい
   - API: ローカルの API サーバーに要求を送って応答を確かめる。外部のサービスや書き込みが絡む部分はモックで置き換える
   - 起動の手順は、ビルトインの `run` スキルがあれば任せる
   - 実環境 (ステージングを含む) には書き込みの要求を送らない。依存のインストール・認証・テスト用データが要るときは、黙って用意せずに聞く
   - 作った検証用のスクリプトとモックは 1 と同じく自分の分だけ消し、立てたサーバーは止める
   - 再現したら高。再現しなかっただけでは取り下げにせず、試した条件を添えて中に置く
4. **実機でしか分からないもの** (実機のデバイス依存、モックでは再現できないタイミング) は、何をどう操作して何が起きたら成立するかを番号付きの手順にする。結果が出るまで中に置く

### 漏れ探し (level が `max` のときだけ)

検証が終わったら、検証済みのリスト (高・中・取り下げ) を渡した新しいサブエージェントを1体立て、**リストに無いものだけ** を探させる。重点は、移動・抽出で落ちたガード、ロック範囲の縮小、副作用のある条件式、テストの setup / teardown の非対称、設定の既定値の反転。無ければ空で返させ、件数を埋めさせない。見つかったものはこの節の手順で検証する。

## 4. 直す判断の土台

3軸の議論はこのルールに沿って意見を出す。

- 直すかどうかは、起こる頻度と起きたときの重さで決める
- 普通に起こりうる不具合と、簡単に直せる不具合は、確認を取らずに直す
- まれにしか起きない不具合は、直すと複雑になり保守性が下がらないかを先に比べる。重篤でなければ見送ってよい (無理な回避はデグレや次の不具合を生む)
- どれだけまれでも、データの破損・不整合や復帰できない状態に陥るものは、回避を検討してユーザーに相談する
- 意図した挙動を変える修正と、レビューの範囲から大きく外れる修正は、その場で直さない (別の作業として報告する)
- 見送ったものは理由と一緒に報告する

## 5. 3軸で議論する

検証で高・中になったものだけを議論にかける。取り下げはかけない。規約違反 (高) は議論にかけず「直す」で決める。仕様・使う人の軸で「聞かないと決まらない」中は、議論にかけずにユーザーに聞く。

pr-review は例外として、中を議論にかけず、起きる条件を示した【確認】の問いとして pending に置く (他人の PR に確定していない指摘を断定で送らないため)。ユーザーが読んで submit するまで相手には届かない。

中で「直す」に決まったものは、確定していないまま直すことになるので、直すことで何を防ぐかを報告に書く。「直さない」「保留」になった中は、何が分かれば確定するかを添えて「確定待ち」として報告する。

### 各軸の判断基準

各軸は全件 (他の軸が出した指摘を含む) に **直す / 直さない / 保留** と1行の理由を出す。

| 軸 | 判断の基準 |
| --- | --- |
| 正しさ | 起きる頻度 × 起きたときの重さ |
| 仕様・使う人 | 利用者に見えるか、依頼・仕様の意図とずれるか |
| 保守・構造 | 直すとどこまで修正が広がるか、複雑さが増えるか |

### 決め方

| 3軸の意見 | 結論 |
| --- | --- |
| 3軸が一致 | その結論で決定 |
| 2対1 | 多数の結論で決定。少数意見を報告に1行残す |
| 保留が2つ以上 (上の2対1より優先) / 3つとも違う | ユーザーに委ねる |
| データの破損・不整合、復帰できない状態に関わる | 意見に関わらずユーザーに委ねる (直し方の案を添える) |

### ユーザーへの聞き方

- 推奨案と、案ごとの違い・推奨の理由を1行ずつ添える
- 互いに独立したものは5件まで1回にまとめてよい。設計判断が要るもの (決め方で他の指摘の直し方が変わる、仕様や方針を決めないと直し方が決まる) は1件ずつ聞く
- 返事で触れられなかったものは、推奨で進めずに保留にする

### 回し方

差分はレビューの対象の差分 (self-review は Step 2 で決めた差分、review-response と pr-review は PR 全体の差分) で数える。

- 差分 (追加 + 削除) が 300 行以下なら、メインが3軸それぞれの基準で順に意見を出し、上の決め方でまとめる
- 300 行を超えたら、各軸に担当サブエージェントを1体ずつ立てる。洗い出しで使った担当がいれば SendMessage で続け、正しさの軸は新しく立てる。全件のリストと §4・§5 の判断基準を渡し、各件への意見を1回だけ返させる。他の軸の意見を見せての往復はしない (費用が増え、意見が似通う)
