# Self Review

自分の差分を **洗い出す → 検証する → 3軸で議論する → 直す → 報告する** の順で回す。判断の基準はすべて `${CLAUDE_PLUGIN_ROOT}/references/principles.md` にある (以下「原則」)。`${CLAUDE_PLUGIN_ROOT}` が未設定のときは、このスキルの base directory から `../../references/` と `../../scripts/` を使う。

## 引数

| トークン | 意味 |
| --- | --- |
| `<PR番号>` / `<PR URL>` | 自分のその PR 全体を対象にする |
| `low` / `medium` / `high` / `xhigh` / `max` | `/code-review` の level (既定 `medium`)。`max` のときだけ漏れ探しをする |
| `branch` | 未コミットの変更があっても、ブランチ全体 (base からの差分) を対象にする |
| `+<観点>` | 原則 §1 の追加観点を足す |

## Step 1: 合うスキルか確かめる

`${CLAUDE_PLUGIN_ROOT}/references/routing.md` の手順で `detect-state.sh [<PR>]` を実行し、扱いに従う。

## Step 2: 対象の差分を決める

上から順に当てる:

1. PR の指定がある → その PR 全体 (`git diff origin/<base>...HEAD`) が対象。直すには手元にその PR のブランチが要るので、`git rev-parse HEAD` が PR の head と違えば、勝手に切り替えずに状態を伝えて相談する
2. `branch` 指定 → `git diff origin/<default_branch>...HEAD` が対象
3. 未コミットの変更がある → 未コミットの変更 (`git diff HEAD` と未追跡ファイル) が対象
4. それ以外 → `git diff origin/<default_branch>...HEAD` が対象

差分の行数 (追加 + 削除) を控える (原則 §5 の回し方で使う)。あわせて、何を求められて作った変更かを1〜3行でまとめる。材料は会話中の依頼、`prepare-context` の CONTEXT.md、PR の説明、チケット。仕様・使う人の軸はこれと照らして見る。

## Step 3: 洗い出す (並行)

原則 §1・§2 に従う。

- 正しさ: Skill ツールで `code-review` を `<level>` で呼ぶ (未コミットが対象なら対象を省き、ブランチ全体ならブランチ名を渡す)
- 仕様・使う人 / 保守・構造: サブエージェントを1体ずつ立てる。渡すもの: 対象の差分の取り方、Step 2 の「求められたもの」、原則のパスと担当する軸の節。自分で書いたコードの意図に引きずられないよう、メインの見立ては渡さない
- 追加観点: 原則 §1 の条件に当たるもの、引数で指定されたものを足す

## Step 4: 検証する

原則 §3 に従い、全候補を高 / 中 / 取り下げに分ける。`max` なら漏れ探しまで行う。

## Step 5: 3軸で議論して決める

原則 §4・§5 に従い、高・中の各件を「直す / 直さない / ユーザーに委ねる」に決める。ユーザーに委ねるものは Step 7 の報告で、原則 §5 の聞き方で聞く。

## Step 6: 直す

- 「直す」に決まったものは、確認を取らずにその場で直す。修正はコミットせず working tree に残す (コミットは本人の実装サイクルに従う)
- テストで再現したものは、同じテストで直ったことを確かめてから検証用ファイルを消す。再発を防ぐ価値があるテストは、既存のテストファイルに正式に足す
- 直したあと、変えたファイルに関係するテスト・lint をそのファイルだけ指定して走らせる。直したことで新しく壊れたものがあれば、それも同じ流れで扱う
- 「直さない」と「ユーザーに委ねる」は触らない

## Step 7: 報告する

`readable-writing` skill があれば使う。ユーザーの判断が要るものを先頭に置く。場所はリポジトリ相対の `path:line`。

```
## セルフレビュー (<対象> / <n> 行 / level <level> / 追加観点: <なし | security, ui>)

### 判断してください
A-1. <要旨> — `path:line` (データ不整合 / 3軸が割れた)
     推奨: <案> / 他の案: <案>

### 確定待ち (確度: 中で、直さない・保留になったもの)
- <要旨> — `path:line`。確定に要るもの: <手順や聞くこと>

### 直したもの (<n>件)
- <要旨> — `path:line` (確度が中なら「防ぐもの: <内容>」、少数意見があれば「<軸>: <理由>」)

### 見送ったもの (<n>件)
- <要旨> — `path:line`。理由: <頻度が低く、直すと〜まで広がる など>

取り下げ <n> 件 (求められたら理由を出す)
```

- 何も見つからなかったら、その旨と見た観点を1行で書く
- 末尾にトークン量の1行を付ける (routing.md の「トークン量の記録」)
