# フェーズA: レビューを作る

理解 → 洗い出し → 重複除去 → 分類 → 検証 → 3軸の議論 → 投稿 → 報告。

投稿に残るのは **検証で裏が取れた指摘 (確度: 高) だけ**。ここを緩めると、実装者が反論に使う時間が増えてレビュー全体の価値が下がる。

## A-0. 先に変更を理解する

指摘の質は、その変更が何をしようとしているかを分かっているかで決まる。PR の規模にかかわらず、洗い出しの前に解説を作る。大きい PR ほど、解説なしでは全体を掴めないため。

`--no-explain` が無ければ、Skill ツールで `explain-change` を呼ぶ (引数は PR 番号か URL)。Artifact の URL をユーザーに渡してから A-1 に進む。explain-change の報告から次を控え、以降で使う:

- 動作確認すると良い点、リファクタリングで `変わる` / `未確認` と判定された箇所 → 影響が major 以上なら A-5 の動作確認として pending に置く。それ以外は A-7 のメモと A-8 の控え
- PR の説明とコードの食い違い → A-3 の【確認】の候補

`explain-change` がインストールされていない (Skill ツールで呼べない) ときは、変更の要点をターミナルに 5 行以内で出して進む。Artifact を作るために別の仕組みを立てない。A-8 の報告の「解説:」の行で、解説を作らなかったことと入れ方を案内する:

> explain-change が入っていないため、解説ページは作っていません。入れると、全体像の図と動作確認すると良い点が付いた解説ページを作り、動作確認の候補もレビューに使えます → `/plugin install explain-change@<marketplace>`

`<marketplace>` は review-kit を入れた marketplace の名前で、`${CLAUDE_PLUGIN_ROOT}` (`~/.claude/plugins/cache/<marketplace>/review-kit/<version>`) から取る。取れなければ `@<marketplace>` を省く。`--no-explain` のときは要点 5 行だけを出し、案内はしない (自分で省いたため)。

## A-1. 洗い出す (3軸 + 追加観点を並行で)

原則 §1・§2 に従う。PR 固有の点だけここに書く。

**正しさ: `/code-review`**

Skill ツールで `code-review` を呼ぶ。引数は `<level> <PR番号>` (level は既定 `high`)。`high` を既定にしているのは、この後の検証で落とす前提だから。洗い出し段階で絞ると、検証すれば成立したはずの問題まで消える。

**保守・構造: サブエージェント**

原則 §1 の保守・構造の観点と §2 (洗い出しの決まり全体。規約違反の条件を含む) を渡す。規約ファイルは `fetch-pr-context.sh` の `rule_files` のうち変更ファイルに関係するもの。対象は `gh pr diff <N>` の変更行だけ。規約違反には「規約ファイル:行番号」とその行の原文引用を必ず付けさせる。

**仕様・使う人: サブエージェント**

正しさと保守・構造は「コードベースの中で正しいか」を見る。だが実際のレビューで効くのは、**コードベースの中では筋が通っているのに、仕様や設計として引っかかる**ところだ。この軸は「コードを読めば答えが出ること」を探さない。**実装者に聞かないと決まらないこと**を探す。

PR の説明に仕様書やチケットの URL があり、手元のツールで読めるなら読む。読めなければ参照不可として進め、レポートにその旨を添える (読めた前提で書くと、書かれていない要件を勝手に補ってしまう)。

```
対象: <repo> の PR #<N> (gh pr diff <N> の差分と、周辺の既存コード)
PR の説明: <pr.body>
仕様書: <読めた場合はその内容 / 読めなければ「参照不可」>
観点: <原則のパス> の §1「仕様・使う人の4観点」(妥当性 / 要件担保 / エッジ / アーキ)

コードから読み取れる「実装された仕様」に対して、レビュアーが確認しておいた方がよい点を
上の4観点で挙げてください。仕様書が参照不可なら [要件担保] は PR の説明の範囲で判断し、
その限界を明記してください。

各項目に重要度を付けてください。軸は「実装の前提が間違っていたときの被害」:
- critical: 取り返しがつかない。データ消失・破損 / 権限・セキュリティ / 課金 / 外部への二重送信
- major: 主要な操作の流れで、利用者に見える挙動が仕様と食い違い得る
- minor: エッジの見た目 / 保守性 / 将来の拡張性

出力の決まり:
- critical → major → minor の順。同じ重要度の中は「実装者に聞かないと決まらない度合い」の順
- 場所は必ずリポジトリルートからの相対パスで `path:line` (範囲は `path:10-20`) と書く
- critical / major は 3 行 (最大 10 件):
  `[重要度][観点] 要旨 — path:line`
  (場所が PR の変更行でなければ、末尾にきっかけになった変更行を `(起点: path:line)` で添える。挙げられなければ `(起点: なし)`)
  `実装: <条件・入力> のとき <挙動>` (コードから読める事実だけ。評価を混ぜない)
  `判断: <Yes/No で答えられる問い>` (何を確認すれば決まるかを含める)
- minor は `[minor][観点] 要旨 — path:line` の 1 行のみ (最大 5 件)
- 件数を埋めるために重要度を上げない。懸念が少なければ件数も少なくてよい
- 同じ趣旨のものは束ねて 1 件にする
- コードを読めば答えが出るもの (= 単なる不具合) は [要件違反] として別に挙げる。仕様書・PR の説明に明記された要件とコードの食い違いで、比べれば確定するもの (例: 空一覧の表示を求めているのに空入力で例外) が対象。A-3 で【不具合】として扱う
```

件数は固定せず、重要度で行き先を決める。critical / major は pending に置いて GitHub で判断し (diff 外を指すものは A-5 の参照コメントにする)、minor はターミナルに 1 行で並べる。上限 (10 件 + 5 件) は、弱い懸念で pending が膨らみ判断の手間が増えるのを防ぐ安全弁で、参照コメントも内数に数える。10 件を超えたら major の下位から minor 側に回し、minor が 5 件を超えたら下位から捨てて、捨てた件数だけ報告する。ユーザーが minor を指定すればそこだけ掘る。

**追加観点**

原則 §1 の条件に当たるもの、引数で指定されたものを足す。破壊的な挙動は【確認】として出し、上の上限とは別に3件までにする (仕様書や PR の説明で決まっていても対象にする)。セキュリティは PR のブランチを checkout 済みなら `/security-review`、それ以外はサブエージェントで見る。

## A-2. 重複を除く

`existing_threads` (他レビュアー・bot の既存スレッド) と突き合わせ、**同じ箇所の同じ趣旨**は落とす。既に出ている指摘を別スレッドで立て直すと、実装者は同じ話に 2 回答えることになる。

`is_resolved: true` のスレッドが同じ箇所を扱っている場合も落とす。一度決着した話の蒸し返しになる。ただし解決時の修正が今のコードで戻っている (再発している) なら落とさず、再発した commit を本文に示して出す。

落とした件数と、誰の指摘と重複したかはターミナル報告に残す。

## A-3. 分類する

各指摘を次で仕分ける。判断に主観を入れないため、**順に当てる**:

| 判定 | 条件 | 行き先 |
| --- | --- | --- |
| 【規約】 | `rule_files` のいずれかの行を引用して「これに反している」と言える | 投稿 (議論にかけない) |
| 【不具合】 | 引用できないが、壊れる経路がある (正しさ・追加観点の指摘と、仕様・使う人の [要件違反]) | A-4 で検証し、高なら A-4.5 の議論を経て投稿 |
| 【改善】 | 保守・構造の整理系 (既存ヘルパーの再利用 / 簡素化 / 効率 / 根本原因の深さ) で、具体的なコストを示せる | A-4 で検証し、高なら A-4.5 の議論を経て投稿 |
| 【確認】 | 仕様・使う人の軸の由来。コードを読んでも真偽が決まらず、仕様・設計 (妥当性 / 要件担保 / エッジ / アーキ) の判断が要る。追加観点「破壊的な挙動」の候補もここに入れる | critical / major は `【確認/<重要度>】` として投稿 (diff 外は A-5 の参照コメント)。minor はターミナルの控え。破壊的な挙動は critical 扱いで、別枠で3件まで |
| 落とす | 上のどれでもない (命名の好み、コストを示せない分割の提案、一般論のベストプラクティス) | — |

「規約に書いてある気がする」で【規約】にしない。**実際にファイルを開いて行を特定する**。特定できなければ【不具合】側で扱う。

周りの既存コードが同じ書き方をしていても、変更行が引用した行に反していれば【規約】として投稿する。落とすかどうかは書き手が決めることなので、本文の最後に「既存の書き方に合わせる判断でしたら、その旨を返信して閉じてください」と添える。

【確認】は検証で裏が取れないので、断定せず実装者への問いの形で pending に置く。そのまま送られても失礼にならず、答えれば閉じられる文面にする。ユーザーは GitHub 上でコードと並べて読み、不要なものだけ削除する。

A-0 の解説で **PR の説明とコードの食い違い** が見つかっていたら、【確認】の候補に加える (実装と説明のどちらが意図どおりかは実装者に聞かないと決まらないため)。重要度は仕様・使う人の軸と同じ基準で付ける。

正しさ・保守・構造の指摘が実は【確認】だった場合 (壊れる経路を示せず、規約も引用できないが、仕様として引っかかる) は【確認】に移す。落とすより、ユーザーの判断に回す方がよい。

## A-4. 検証する

**【不具合】と【改善】は全件、原則 §3 で高 / 中 / 取り下げに分ける。** 第一手段はテストでの再現。`max` なら漏れ探しまで行う。

- 高 → A-4.5 の議論を経て投稿
- 中 → 断定せず、起きる条件を示した `【確認/<重要度>】` の問いとして投稿する (影響が minor なら投稿せずターミナルの控え)。実機でしか分からないものは、確かめる手順を本文に添える
- 取り下げ → 否定する行を引用できたものだけ。引用できなければ中に置く

**【規約】は検証不要。** 引用した行がそのまま根拠になる (確度: 高)。

## A-4.5. 3軸で議論して重さを決める

高の【不具合】と【改善】を、原則 §4・§5 で議論する。他人の PR なので、結論は「直すか」ではなく **指摘の重さ** として文面に出す:

| 議論の結論 | 文面での重さ |
| --- | --- |
| 直す | 必須。そのまま修正を求める |
| 直さない (頻度が低い・影響が小さい) | 任意。末尾に「任意です」と理由を1行添える |
| 直さない (保守・構造の軸が、直すと修正が広く及ぶとした) | 末尾に「影響範囲が広いので、別 PR での対応でも構いません」と添える |
| ユーザーに委ねる | 起きることと直すと及ぶ範囲を書き、この PR で直すか別 PR にするかを問う `【確認/<重要度>】` として投稿する |

2対1 で決まったものは、少数意見を A-7 のメモと A-8 の控えに1行残す (相手には送らない)。

## A-5. 文面を書く

1 コメントは **タグ + 3 要素 + 最大 5 行**。コードブロックは多くて 1 つ。長いと読み飛ばされ、読み飛ばされた指摘は直らない。

言語は PR の説明・既存コメントに合わせる (日本語のリポジトリなら日本語)。

**【不具合】** — 何が起きるか / どう確かめたか / 直し方:

```
【不具合】options 未指定で呼ぶと落ちる

createClient() を引数なしで呼ぶ経路があり、options.retry で TypeError になります。
テストを書いて実行し、実際に落ちることを確認しました。
`options?.retry` で回避できます。
```

A-4.5 で任意・別 PR でよいとなったものは、最後の行に重さを添える:

```
【不具合】リトライ中に画面を閉じると通知が二重に出る

閉じる操作と 3 回目のリトライが重なると、onDone が 2 回呼ばれます (retry.ts:40 → 72)。
重なる時間は数十ミリ秒なので、任意です。
```

**【改善】** — 何のコストか / 根拠の行 / 直し方。重さは【不具合】と同じく添える:

```
【改善】日付の整形が既存ヘルパーと重複

src/utils/date.ts:15 の formatDate() と同じ処理です。
こちらを呼べば 12 行消せます。任意です。
```

**【規約】** — どの規約か / 現状との差分:

```
【規約】docs/rules/error-handling.md:42

「API 呼び出しの失敗は共通ハンドラに委譲する」
この catch で個別に握りつぶしています。
```

規約違反が 3 件以上あるときは、1 件にまとめて最初の違反の行に置く (1〜2 件なら各行に置く。行から離れると、どこの指摘か分かりにくくなるため):

```
【規約】規約違反がまとめて 3 件あります

次の箇所が規約に反しています。確認のうえ、必要なら修正してください。
- `src/app/bar.ts:42` docs/rules/error-handling.md:42「API 呼び出しの失敗は共通ハンドラに委譲する」
- `src/app/baz.ts:10` docs/rules/naming.md:8「…」
- `src/app/qux.ts:77` docs/rules/error-handling.md:42 (上と同じ)
```

**【確認/<重要度>】** — 仕様・使う人の軸の `実装` / `判断` をそのまま実装者向けの問いにする。重要度 (critical / major) は相手に温度感を伝えるために付ける。観点 ([エッジ] など) は付けない:

```
【確認/major】上限超過時の扱い

件数が上限を超えた場合の分岐がなく、現状は黙って切り捨てられます。
意図した挙動でしょうか。
```

断定せず問いの形にする。仕様の判断は実装者の側にあり、こちらが決めることではない。同じ形で、次も【確認】として書く:

- 確度が中の不具合の疑い: 「〜と〜が重なると、〜になる可能性があります。考慮済みでしょうか」
- 3軸が割れた指摘: 「〜が起きます。直すと〜まで及ぶので、この PR で直すか別 PR にするか相談させてください」
- 動作確認: 「設定の保存が同期になったので、画面を閉じた直後に開き直しても値が残るか、確認できていますか」 (手順が要るものは本文に番号付きで添える)

破壊的な挙動は、仕様で決まっていても念のための確認として書く:

```
【確認/critical】不整合時の上書き

同期で不整合を見つけると、端末側の値でサーバーの値を上書きします (sync.ts:40)。
上書き前の値は残らないので、念のため意図どおりか確認させてください。
```

**参照コメント (diff 外を指す【確認】)** — GitHub は diff 外の行にコメントを置けないので、起点 (きっかけになった変更行。仕様・使う人の担当が出していなければ自分で特定する) に置き、1 行目で本当の場所を示す:

```
【参照・diff外】[`src/app/store.ts:12`](https://github.com/<owner>/<repo>/blob/<head_oid>/src/app/store.ts#L12)
【確認/major】状態の持ち方が既存の store と二重

この行で追加した選択状態を、store でも保持しています。
どちらを正とするか決まっていますか。
```

- 1 行目は相手に送っても通じる形にしてある。フェーズB はこの行で本当の場所を拾う
- リンクは `head_oid` 固定の permalink にする (branch 名だと後の commit で行がずれる)。範囲は `#L10-L20`
- 本文の 1 文目で、置いた行の変更と本当の場所の関係を書く
- 起点が無いものは diff で最初に現れる追加行に置き、1 文目を「変更全体に関わる確認のため、最初の変更ファイルに置いています」とする
- diff 外かどうかは `post-pending-review.sh --dry-run` の `invalid` で確かめられる

**件数を絞る。** pending は 1 PR あたり 12 件まで (「その他」を含む) にする。多いと読まれなくなるため。超えるときは次の優先順位の低い側から外し、外したものは「その他」のコメント 1 件にまとめる。確認が要るものを pending から消すのではなく、まとめて残す。

1. 必須の不具合
2. critical の【確認】・破壊的な挙動
3. major の【確認】
4. 確度が中の【確認】
5. 動作確認の【確認】
6. 任意・別 PR 可の不具合と改善、規約 (まとめたものも 1 件と数える)

```
【確認】その他の指摘 (5 件)

件数が多いため、まとめて置いています。それぞれ確認のうえ、必要なら対応してください。
- `src/app/foo.ts:120` [改善・任意] 日付の整形が formatDate() と重複
- `src/app/view.ts:42` [動作確認] 権限なしで開いたときに一覧が空表示になるか
- …
```

「その他」は外したものの中で最も優先順位が高いものの行に置く。

書けたら JSON にまとめる (`line` は **新しいファイル側の行番号**。参照コメントは起点の行):

```json
[
  {"path": "src/app/foo.ts", "line": 88, "body": "【不具合】..."},
  {"path": "src/app/bar.ts", "line": 42, "body": "【規約】..."},
  {"path": "src/app/list.ts", "line": 30, "body": "【確認/major】..."},
  {"path": "src/app/view.ts", "line": 15, "body": "【参照・diff外】[`src/app/store.ts:12`](...)\n【確認/major】..."}
]
```

## A-6. 投稿する (確認不要)

```bash
bash ${CLAUDE_PLUGIN_ROOT}/skills/pr-review/scripts/post-pending-review.sh <PR番号|URL> <comments.json>
```

pending review は本人にしか見えないので、ここは確認を取らずに投稿してよい。ユーザーは GitHub 上でコードと並べて精査する。

| exit | 意味 |
| --- | --- |
| 0 | 投稿成功。`invalid` に除外分が入る |
| 5 | 投稿可能なコメントが 0 件 (全件が diff 外の行) |
| 6 | 既に未 submit の pending review がある。破棄を促して終了 |

スクリプトは投稿前に diff と行番号を突き合わせる。GitHub は diff に無い行へのコメントを 422 で弾き、**1 件でも不正だと全件落ちる**ため、除外して投稿する。`invalid` が出たら行番号を取り直して 2 回目を投げるか、その指摘を落とすか判断する。【確認】が diff 外の行を指している場合は取り直さず、A-5 の参照コメントに直す (先に `--dry-run` で `invalid` を見ておけば 1 回の投稿で済む)。

2 回目以降 (行番号の取り直し、実機確認後の追加) は、最初の出力の `review_id` を `--append <review_id>` で渡して同じ pending に追記する。ID が一致しない pending はユーザーが手で書いたドラフトとみなし、exit 6 で止まる。

レビュー本文 (全体コメント) は **空のままにする**。相手に一番強く届く部分なので、submit 時にユーザーが自分の言葉で書く。

## A-7. 引き継ぎメモを残す

修正確認 (フェーズB) は数日後の別セッションになることが多い。そのとき PR の理解や指摘の根拠を最初から作り直すと、トークンの大半がそこに消える。フェーズB に要るのは **何を・なぜ指摘し・どう確かめ・どうなれば閉じるか** だけなので、それだけを `fetch-pr-context.sh` の `review_memo.path` に書き残す。ディレクトリが無ければ作る。

```markdown
# PR #<N> <title>
<url> / レビュー時点: <head_oid 先頭7桁> / <日付>

## 変更の要点
<3〜5行。何をなぜ変える PR か>

## 投稿した指摘
### 1. 【不具合】foo.ts:88 options 未指定で TypeError
- 根拠: createClient() を引数なしで呼ぶ経路がある (bar.ts:20)
- 検証: テストで再現
  (テスト本文をそのまま貼る。ファイルは削除済みなのでここにしか残らない)
- 閉じる条件: options 未指定でも落ちない (上のテストが通る)

### 2. 【規約】bar.ts:42 共通ハンドラを通っていない
- 根拠: docs/rules/error-handling.md:42「API 呼び出しの失敗は共通ハンドラに委譲する」
- 閉じる条件: catch が共通ハンドラに委譲される

## 仕様・設計の確認事項
- [critical][妥当性] 失敗時の自動リトライで二重実行にならないか — src/app/api.ts:88 (pending / レポートのみ)
- [major][アーキ] 状態の持ち方が既存の store と二重 — src/app/store.ts:12 (参照: src/app/view.ts:15 に置いた)

## 動作確認
- [挙動変化/変わる] 設定の保存が非同期から同期になった — settings.ts:88 (pending: ① 設定画面を開く ② 値を変えてすぐ画面を閉じる ③ 再度開いて値が残っているか)
- [実機確認] qux.ts:142 (控えのみ: ① 一覧を開く ② 絞り込みを変更 ③ 表示が崩れるか)

## 確度: 中で【確認】にしたもの
- retry.ts:55 タイムアウトと応答が同時に来ると二重処理の可能性。確定に要るもの: 応答ハンドラの呼ばれ方を実機ログで確認

## 投稿しなかった指摘
- baz.ts:20 型定義上 null にならない (取り下げ: types.ts:12 `id: string`)

## 少数意見
- foo.ts:88 保守・構造: 呼び出し元 12 か所に波及するため別 PR を推す
```

**閉じる条件**が一番大事。フェーズB の ✅ / ⚠ 判定がこれで客観的になる。**確度: 中で【確認】にしたもの** と **投稿しなかった指摘** は、再レビューで同じものを蒸し返さないために残す (1 行ずつでよい)。

書かないもの: 探索の経路、code-review や Agent の生出力、試して外れた仮説の過程。メモは数 KB に収める。長いメモは読み直すコストが高く、残す意味が薄れる。

A-8 の後に minor を pending に追加したり、実機確認の結果を受けて投稿を足したりしたら、メモも同じ内容に更新する。

## A-8. 報告する

確認が要るものはすべて pending にあるので、ターミナルは **pending に何を置いたかの件数と、見なくてよい控え** だけにする。冒頭で、見るべきものは pending にあると1行で伝える。場所はすべてリポジトリ相対の `path:line` で書く。

```
## PR #<N> <title>
pending に <n> 件置きました。確認が要るものはすべてそちらにあります → <url>/files
ブランチ: `<head>` を checkout しました (切り替え前: `<元のブランチ>`) ※ checkout したときだけ
解説: <Artifact URL> (作らなかった場合はその理由と 5 行以内の要点)

内訳: 不具合 <n> (必須 <n> / 任意 <n> / 別 PR 可 <n>) / 改善 <n> / 規約 <n> (まとめた場合はその旨) / 確認 critical <n>・major <n> (うち確度: 中 <n>、3軸が割れたもの <n>、動作確認 <n>、破壊的な挙動 <n>) / 「その他」にまとめたもの <n>

--- 以下は見なくてよい控え ---
minor: [エッジ] 0 件時の表示に空表示の分岐がない — `src/app/foo.ts:120`
動作確認 (影響が小さいもの): `src/app/qux.ts:142` ① 一覧を開く ② 絞り込みを変更 ③ 表示が崩れるか
投稿しなかったもの: 取り下げ <n> / 好み <n> / 重複 <n>
少数意見: `src/app/foo.ts:88` 保守・構造: 呼び出し元 12 か所に波及するため別 PR を推す
※ 仕様書リンクは参照不可のため、[要件担保] は PR の説明の範囲で判定
トークン: <usage-report の1行> (routing.md の「トークン量の記録」)
→ 引き継ぎメモ: <review_memo.path> (修正後は新しいセッションで `/pr-review <N>`)
```

- 【確認】は **critical / major 最大 10 件 (pending) + minor 1 行 × 最大 5 件 (控え)**。破壊的な挙動はこれとは別に 3 件まで。迷ったら「実装者に聞かないと決まらないか」で切る
- minor は、ユーザーが場所で指定したら詳細化して pending に追記する (`--append`)
- 投稿済みの一覧・取り下げの理由・重複の相手は、ユーザーが求めたときだけ表で出す
- 検証テストを書いた場合は、その本文を末尾に添える (ファイルは削除済みなので、ここにしか残らない)
