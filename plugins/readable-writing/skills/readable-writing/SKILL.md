# readable-writing

人が読む文章を、上の層だけで概要がわかり、詳細は必要なときに引ける形に組み立てるための原則集。扱うのは構成と情報の並べ方。言い回しは `principles.md` 末尾に最低限だけ置き、詳しくは remove-ai-tone に任せる。

## 1. 文脈を判定する

書き始める前に、依頼・媒体・既存の文章から次の軸の値を決める。決められない軸は「不明」とし、その軸を条件に持つ原則は使わない。

| 軸 | 値 |
| --- | --- |
| 目的 | 判断してもらう / 把握してもらう / 実行してもらう / 後で引いてもらう / 理解してもらう |
| 読み手の前提知識 | ある / 一部ある / ない |
| 読み手との関係 | 自分 / チーム / 他チーム / 社外 |
| 読まれ方 | 1回だけ / 何度も参照される / 流し読みされる |
| 媒体の性質 | 図が使えるか、表が使えるか、折りたたみが使えるか、長さの上限があるか、ターン制の対話か |

- 目的は今の段階で1つに決める。複数に当てはまるときは、読み手に最初にしてほしい行動で決める(報告の中に確認事項があるなら「判断」)
- 段階で目的が変わる文書(合意までは判断、合意後は後で引く、など)は、今の段階の目的で書き、段階が変わったら並べ替える
- 媒体は製品名ではなく性質で判定する。例: PR description は図(mermaid)・表・折りたたみが使える、チャットの投稿は表が崩れることがある、Claude のセッションはターン制の対話

## 2. 優先順位

ユーザーの明示的な指示 > その文書専用の skill(PR description を書く skill など)・媒体やリポジトリの既存テンプレート・慣習・CLAUDE.md > このSkill

- その文書専用の skill があるときはそちらの手順と構成に従い、このSkillは各節の中の並べ方の補助にだけ使う
- 既存テンプレートの見出しは変えず、各見出しの中の並べ方にこの原則を使う
- テンプレートとこの原則が食い違うときは、テンプレートに従い、違いを一言だけ伝える

### 既存の文書を書き直すとき

- 中身(事実・決定・数値・コード)は変えず、並べ方と言い回しだけを変える
- 誤りや食い違いを見つけても直さず、該当箇所に「要確認」として残し、ユーザーに伝える

## 3. 原則の読み方

- 各原則は理由とセットで書いている。理由が今の文書で成り立たない場面では、その原則を使わない
- 数値はすべて目安。超えたら見直すきっかけにする
- 例は当てはめ方の一例で、そのまま写すものではない
- 原則どうしがぶつかるときは、読み手が最初にしてほしいことに近い方を優先する

## 4. 読むもの

1. `references/principles.md` を常に読む
2. 目的の reference を1つだけ読む

| 目的 | reference |
| --- | --- |
| 判断してもらう(確認・提案・比較・レビュー依頼) | `references/purpose/decision.md` |
| 把握してもらう(報告・進捗・サマリ) | `references/purpose/report.md` |
| 実行してもらう(手順・依頼) | `references/purpose/procedure.md` |
| 後で引いてもらう(README・仕様・ナレッジ) | `references/purpose/reference.md` |
| 理解してもらう(解説・設計の説明) | `references/purpose/explain.md` |

3. 媒体がターン制の対話なら `references/conversation.md` も読む

ほかの reference は読まない。同じセッションですでに読んだ reference は読み直さない。

## 5. 受付箱(候補を溜める)

作業中にユーザーが文章の構成を直した・却下したとき、その直しがこのSkillにない、またはこのSkillと逆なら、聞かずに `~/.claude/readable-writing/inbox.md` に候補として追記する。ファイルがなければ作る。

- 候補は採用されるまで原則として使わない
- 書かないもの: その文章限りの判断、すでにこのSkillにあるもの、言い回しの直し
- プロダクト名・人名など固有の情報は書かず、一般化して書く

```markdown
### <原則の案>
- 条件: <軸=値。なければ「なし」>
- 理由: <ユーザーの直しから読み取れる理由>
- 出典: <YYYY-MM-DD> / <直しの要旨>
```

### 取り込む

ユーザーが「受付箱を取り込んで」と言ったら、dotfiles リポジトリの `plugins/readable-writing/` で次を行う。

1. 候補の一覧を、採用・不採用・保留の案と理由を付けて1つの表で示し、採否をまとめて聞く
2. 採用されたものを合う reference に移す。「出典」行は移さない(公開リポジトリのため)
   - 既存の原則にまとめられるなら、新しく足さずにまとめる(発動のたびに読む量を増やさないため)
   - `principles.md` が300行に近づいたら、原則をまとめるか目次を付ける
3. 受付箱から、採用・不採用が決まった項目を消す
4. version を上げて CHANGELOG に書く
