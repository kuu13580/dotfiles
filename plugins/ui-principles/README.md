# ui-principles

プロダクトの特性によらない UI/UX の原則集 skill。画面やコンポーネントの実装、UIレビュー、文言作成、入力フローの設計で自動発動し、文脈に合う原則だけを参照する。

## いつ発動するか

- 画面・コンポーネントを新しく作る・直す(Web・ネイティブアプリ)
- UIのレビューや改善の相談
- ボタン・エラー・空の状態などの文言を作る
- 入力フローや画面遷移を設計する

バックエンドだけの変更、CLI/TUI の出力には使わない。見た目の方向性(配色・フォント選び・個性)は `frontend-design` に任せ、こちらは使いやすさを担当する。

## 仕組み

1. **文脈を判定する**: 幅 / 入力手段 / 利用頻度 / トーン / プラットフォーム / 言語 / 機能 の7軸で、今の画面の文脈を決める
2. **振り分け表で reference を選ぶ**: 作業の種類(文言だけ直す → `copy.md` など)、作る部品(ダイアログ → `dialog.md` など)、文脈(狭い幅 → `mobile.md` など)で、読むファイルを絞る
3. **条件が合う原則だけ使う**: 各原則は「見出し〔必須/推奨〕/ 適用条件 / 理由 / 例」。理由が今の文脈で成り立たなければ使わない

優先順位は「ユーザーの指示 > プロダクトの既存デザインシステム・慣習 > このSkill」。実装では既存に従い、レビューでだけ違いを指摘する。

| ファイル | 中身 |
| --- | --- |
| `SKILL.md` | 文脈の判定、優先順位、必須の原則の一覧、振り分け表、受付箱の運用 |
| `references/*.md` | どの画面でも読むもの(layout / actions / feedback / form-flow / copy)、部品を作るときだけ読むもの(dialog / step-input / consent / navigation / notification / motion / ai-features / map)、文脈で足すもの(mobile / desktop / responsive / implementation) |

## 受付箱(こだわりを育てる)

作業中にユーザーが UI を明示的に直した・却下したとき、そのこだわりが Skill にない(または逆)なら、Claude がタスクの区切りで「ui-principles に入れますか?」と聞く。「はい」なら `~/.claude/ui-principles/inbox.md` に原則の形で追記し、次に発動したときから反映される。

正式な reference への取り込みは、このリポジトリで「受付箱を取り込んで」と頼む。合う reference へ移し、ギャラリーの図解を足し、受付箱から消し、version を上げて PR にする。受付箱の「出典」行(プロジェクト名や発言)は reference に移さない。

## ギャラリー(人が見る用)

原則を NG 例・OK 例付きで見られる静的ページ: https://kuu13580.github.io/dotfiles/ui-principles/

ソースは `docs/ui-principles/` で、GitHub Pages(main の `/docs`)から公開している。Claude は読まない。

- 生成: `python3 docs/ui-principles/build.py`(references と `examples.json` から `index.html` を作る)
- `examples.json` は原則の見出しをキーにした図解。見出しを変えたらキーも合わせる(合わないものは実行時に警告が出る)

## 原則の出どころ

Web 調査(NN/g、Laws of UX、Baymard、WCAG、Apple HIG、Material Design、公開デザインシステム(GOV.UK・Carbon・Atlassian・Primer・SmartHR・デジタル庁ほか)、Vercel Web Interface Guidelines、著名デザイナーの記事など)を中心に、約1,400件の Tips を重複統合して候補にし、ユーザーの判定と好みの傾向で222件に絞った。

## 意図的に入れていないもの

受付箱から取り込むときも、この範囲に当たるものはユーザーに確認してから入れる。

| 種類 | 理由 |
| --- | --- |
| 見た目の方向性(配色・フォント選び・個性の出し方) | `frontend-design` の担当 |
| アクセシビリティ準拠(WCAG・読み上げ・コントラスト比・フォーカス表示) | 量が多く、別の仕組みで扱う想定。キーボードショートカットなど操作のUXに関わるものは入れている |
| 機能別の細則(AI・一覧/表・検索・地図・グラフなど) | プロダクトの雰囲気に左右される。プロダクトで作りながら受付箱で条件付きで足す。採用済みの一部は残している |
| 文言の表記細則(語尾の統一、助詞、英語の言い回しなど) | 細かすぎて効果が薄い。文言の大原則と「、」「・」の使い分けだけ入れている |
| 見た目の細則(字の太さの段階、揃え方の混在など)と、ブラウザ固有の癖 | 細かすぎる、または特定の環境に依存する |
| 開発プロセス・計測の話 | UIの原則ではない |
