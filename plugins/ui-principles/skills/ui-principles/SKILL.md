# ui-principles

プロダクトの特性によらないUI/UXの原則集。各原則には適用条件と理由がある。条件に合わない場面や、理由が成り立たない場面では使わない。

## 1. 文脈を判定する

作業を始める前に、コードベース・既存の画面・ユーザーの指示から次の軸の値を決める。決められない軸は「不明」とし、その軸を条件に持つ原則は使わない側に倒す。

| 軸 | 値 |
| --- | --- |
| 幅 | 狭い / 広い / 両方(複数の幅に対応する) |
| 入力手段 | タッチ / ポインタ / キーボード(複数可) |
| 利用頻度 | たまに(初めて・たまに使う) / 日常(毎日・業務で使う) |
| トーン | カジュアル / フォーマル |
| プラットフォーム | Web / iOS / Android(複数可。ネイティブで未定なら不明) |
| 言語 | 日本語 / 英語 |
| 機能 | 入力フォーム、登録・作成、ステップ入力、ダイアログ、ボトムシート、通知、一括操作、AI生成・提案、地図 など、作る画面に含まれるもの |

利用頻度とトーンは画面ごとに変わりうる(同じプロダクトでも、たまに使う作成フローと毎日使う一覧がある)。プロダクト全体ではなく、その画面の作業をどれくらいの頻度で行うかで判定する。

プラットフォームは、依頼の言葉(「スマホアプリ」など)だけで決めず、コードベースの技術スタックで判定する。決められなければ不明とする。

7軸の外に自由記述の条件もある(例:「既存のUI部品があるとき」「取り消せない操作のとき」)。コードベースや依頼の内容から、その場で判定する。

## 2. 優先順位

ユーザーの明示的な指示 > プロダクトの既存デザインシステム・既存UIの慣習・CLAUDE.md > このSkill

- 実装するとき: 既存の作りに黙って従う。このSkillを理由に既存を変えない
- 依頼の範囲を超える改善(文言だけの依頼で、エラーの出し方も直したほうがよい場合など)は、勝手に広げず提案として一言添える
- レビューするとき: このSkillとの違いを指摘してよい。直すかどうかはユーザーが決める
- 〔必須〕に反する指示にも従う。ただし一言だけ指摘する

## 3. 原則の読み方

- 形式は「見出し〔強さ〕/ 適用条件 / 理由 / 例」。適用条件がすべて今の文脈に当てはまるときだけ使う。条件のない原則はどこでも使う
- 条件に当てはまっても、理由が今の文脈で成り立たないなら使わない。〔必須〕も同じで、条件と理由の前提が成り立つ場面では例外なく守る
- 条件には、設計の中で決まるものもある(例:「1画面に1問ずつ聞く入力」)。その設計を選んだ時点で、その条件の原則も使う
- 「項目が多い」「長いフォーム」などの量は、1画面で全体を見渡せるかを目安に判断する
- 〔推奨〕は既定のふるまい。文脈に合わなければ外れてよい。〔必須〕は破ると不具合とみなす
- 各 reference の末尾の「チェックリスト」は理由のない1行の原則。実装後の点検に使う
- 例は当てはめ方の一例で、そのまま写すものではない

## 4. 必須の原則(常に守る)

詳しい理由と例は各 reference にある。適用条件がある原則は、条件に当てはまるときだけ守る。

- 一覧の各項目は、行や位置ごとの役割を全項目でそろえる(条件: 機能=一覧比較) → layout.md
- カードを押せるようにするなら、カード全体を押せる範囲にし、押せることを見た目で示す(条件: カードを押せるようにするとき) → actions.md
- 0件や空欄のまま進むときは、ボタンの文言もその結果を表す言葉に変える(条件: 1つの選択や入力の結果を確定するボタンがある画面(ステップ入力・選択画面など)) → copy.md
- 生のHTML要素などで独自に作らずプロダクトの既存UI部品を使い、ない部品を仮に作るときも既存の見た目に合わせる(条件: 既存のUI部品があるとき) → layout.md
- ボタンの色を画面ごとに上書きせず、部品に用意された種類(主・副など)を使う → layout.md
- 地図の端に近いラベルは、はみ出さない向きに出す(条件: 機能=地図) → map.md
- 権限・資格・容量・サービス障害など入力に起因しない問題は入力欄のエラーにせず状況と次の手を伝え、権限がないと事前に分かるなら入力前に説明する → feedback.md
- ダイアログでの操作は処理が完了するまでダイアログを閉じず、失敗したらダイアログの中で該当箇所とエラーを示す(条件: 機能=ダイアログ) → dialog.md
- 複数ページにまたがるフォームを、ブラウザの戻る操作で壊さず、前のページを入力済みの状態で表示する(条件: 機能=ステップ入力、プラットフォーム=Web) → step-input.md
- 保存・送信・検証に失敗しても、ユーザーが入力・アップロードした内容を、誤った値も含めて消さない → form-flow.md
- 送信中は処理中であることを示して二重送信を防ぎ、画面側だけでなくサーバー側でも重複を防ぐ → form-flow.md
- エラー文は、未入力なら何をすればよいかを指示し、不正な値なら満たすべき条件を説明する → copy.md
- 目的と無関係な行為(アプリのダウンロード、メルマガ登録、アカウント作成など)を交換条件にせず、複数の同意を1つの操作にまとめない → consent.md
- ユーザーの利益にならない選択肢(定期購入、追加購入、データ共有、マーケティング受信など)を既定で選んだ状態にせず、本人に選ばせる → consent.md
- 断る選択肢や警告・確認の文言は中立的に書き、罪悪感や不安をあおったり結果をごまかしたりして判断を誘導しない → consent.md
- 返金不可など判断に影響する重要な条件を、小さく薄い文字や予想外の位置で示さない → consent.md
- 一度断られた依頼や閉じられた宣伝を繰り返し出さず、断る選択肢を「後で」だけにしない(条件: 許可の依頼や宣伝を出すとき) → consent.md
- 二重否定や、チェックすると拒否になるような紛らわしい文言を使わず、同じ画面の中で同意の向きを反転させない(条件: 同意や購読の選択) → consent.md
- サーバーで描画したページにスクリプトが動きを付けるときに、利用者が入力し始めた値やフォーカスを消さない(条件: プラットフォーム=Web、サーバー描画後にクライアントで動かす構成) → implementation.md
- フォーム内の送信以外のボタンが、押しただけでフォームを送信しないようにする(条件: プラットフォーム=Web) → implementation.md

## 5. 振り分け表

作業の種類で引き、部品と文脈で足す。当てはまる行が複数あれば、すべての行の reference を合わせて読む(同じものを二度読まない)。

### 作業の種類で引く

| 作業 | 読む reference |
| --- | --- |
| 画面や部品を新しく作る・作り直す | layout.md, actions.md, feedback.md(入力欄があれば form-flow.md、文言を書くなら copy.md も) |
| 入力フォームを作る | form-flow.md, copy.md, feedback.md |
| 文言だけを作る・直す | copy.md |
| ボタン・操作の配置・取り消し | actions.md |
| 読み込み・進捗・エラー表示 | feedback.md |
| Webでの実装の細部(入力欄の属性、ホバー、幅の切り替えなど) | implementation.md |
| UIのレビュー | 対象の画面に関わる reference をすべて |

### 部品で足す(作る画面に含まれるときだけ)

| 部品 | 足して読む reference |
| --- | --- |
| ダイアログ・モーダル・シート・確認ダイアログ | dialog.md |
| ステップ入力(1問ずつ進むフロー・確認画面) | step-input.md |
| 同意・課金・解約・購読・許可の依頼・宣伝 | consent.md |
| ナビゲーション・タブ・メニュー | navigation.md |
| アプリ内のトースト・バナー・状態メッセージ・作業への割り込み表示(ほかのユーザーへ送る通知は含まない) | notification.md |
| アニメーション・画面の切り替え(ステップ間の遷移を含む) | motion.md |
| AIによる生成・提案 | ai-features.md |
| 地図 | map.md |

### 文脈で足す

| 文脈 | 足して読む reference |
| --- | --- |
| 幅=狭い、または入力手段=タッチ | mobile.md |
| 幅=広い | desktop.md |
| 幅=両方(複数の幅に対応) | mobile.md, desktop.md, responsive.md |
| プラットフォーム=Web で実装まで行う | implementation.md |

## 6. 受付箱(こだわりを育てる)

ユーザーが作業中に示したこだわりを、次のプロダクトから効かせるための仕組み。

### 読む
発動したら `~/.claude/ui-principles/inbox.md` があるか確認し、あれば読む。中身はユーザーが追加を承認した原則で、reference と同じ形式・同じ読み方で使う。reference と食い違うときは受付箱を優先する(ユーザーのより新しい判断のため)。

### 聞く
作業中にユーザーがUIについて明示的に直した・却下したこだわりがあり、それがこのSkillにない、またはこのSkillと逆なら、タスクの区切りでまとめて聞く。

> このこだわりを ui-principles に入れますか?
> (原則・適用条件・理由に一般化した文案)

- 作業の途中では割り込まない
- 聞かないもの: そのプロダクトでしか成り立たない話、その場限りの判断、すでにこのSkillにあるもの
- 「はい」なら受付箱に追記する。ファイルやディレクトリがなければ作る

```markdown
### <原則>〔推奨〕
- 適用条件: <軸=値。なければ「なし」>
- 理由: <…>
- 例: <…>
- 出典: <プロジェクト名> / <YYYY-MM-DD> / 「<ユーザーの発言>」
```

### 取り込む
ユーザーが「受付箱を取り込んで」と言ったら、この plugin のソース(dotfiles リポジトリの `plugins/ui-principles/`)で次を行う: 各項目を合う reference に移す(合うものがなければ reference を足して振り分け表に追記)、取り込んだ原則の NG 例・OK 例を `docs/ui-principles/examples.json` に足して `python3 docs/ui-principles/build.py` を実行する(人が見るギャラリー。この Skill の実行時には読まない)、受付箱から取り込んだ項目を消す、plugin の version を上げて CHANGELOG に書く、PR を作る。

- 「出典」行(プロジェクト名・ユーザーの発言)は reference に移さない。公開リポジトリに作業中のプロダクトの情報を出さないため
- 原則・適用条件・理由・例に入っているプロダクト名・固有の値・ユーザーの発言も、そのまま移さず一般化してから移す。同じ理由
- README の「意図的に入れていないもの」に当たる項目は、取り込む前にユーザーに確認する
