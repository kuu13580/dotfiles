# Web実装の細部

読む場面: Webで実装まで行うとき。条件がない原則はどこでも使い、条件がある原則は当てはまるときだけ使う。

## 原則

### 幅によるレイアウトの切り替えはできる限りCSSで行い、JSでの幅判定は避ける〔推奨〕
条件: プラットフォーム=Web ／ 理由: JSの判定は描画後に走り、一瞬別のレイアウトでちらつき、サーバー描画とも食い違う。
例: メディアクエリやコンテナクエリで切り替える。

### 主要な入力欄が1つだけの画面では、ポインタ操作の端末なら開いた時点でフォーカスし、タッチ端末では自動でフォーカスしない〔推奨〕
条件: 主要な入力欄が1つだけの画面 ／ 理由: デスクトップではすぐ入力でき、タッチではキーボードが画面を覆いレイアウトが動く。

### Enterキーの挙動は入力の種類の慣習に合わせ、1行の入力ではEnterで送信、複数行の入力ではEnterで改行できるようにする〔推奨〕
条件: プラットフォーム=Web ／ 理由: 複数行でEnterを送信にすると改行できず誤送信を招く(チャット欄はEnter送信・Shift+Enter改行でよい)。
例: 1行の欄はform要素で囲んで標準の送信を使い、複数行の欄は⌘/Ctrl+Enterで送信する。

### 入力欄には目的に合ったautocomplete属性と意味のあるnameを付け、ブラウザやパスワードマネージャーの自動入力を働かせる〔推奨〕
条件: プラットフォーム=Web ／ 理由: 自動入力で手間とミスが減り、type属性だけでは欄の目的(本人のメールか他人のか)が分からない。
例: サインインのパスワード欄に autocomplete="current-password"、新規設定は "new-password"。
数値: WCAG 2.2 SC 1.3.5 (AA)

### 数値を入力する欄では数字用のキーボードを出し、ホイールで値が変わるなど副作用がある数値専用の入力型は、増減操作が要る欄にだけ使う〔推奨〕
条件: プラットフォーム=Web ／ 理由: type="number" はスクロールで値が意図せず増減し、数字以外を入れても反応がない。
例: テキスト型に inputmode="numeric" と pattern を付け、形式は送信時にも検証する(数量を増減する欄は type="number" も可)。

### 画面上のキーボードが出たときに、入力欄や下部に固定したUIが隠れないようにする〔推奨〕
条件: プラットフォーム=Web、入力手段=タッチ ／ 理由: 既定ではキーボードは見えている領域だけを縮め、レイアウトは追従しない。
例: 下部固定のパネルは Visual Viewport API で高さを測りキーボードの上に置く。

### アニメーションでレイアウトの再計算や再描画を毎フレーム起こすプロパティを動かさず、移動・拡縮・透明度の変化で表現する〔推奨〕
条件: プラットフォーム=Web ／ 理由: transform と opacity は合成だけで安価だが、レイアウト系は毎フレーム再配置しカクつく。

### ホバーの見た目はホバーできる端末に限って適用し、どの端末でも機能する既定の見た目を先に用意する〔推奨〕
条件: プラットフォーム=Web ／ 理由: タッチ端末では押した瞬間にホバー状態が出て貼り付き、誤ったフィードバックになる。
例: ホバーの強調を @media (hover: hover) の中に書く。

## チェックリスト

- サーバーで描画したページにスクリプトが動きを付けるときに、利用者が入力し始めた値やフォーカスを消さない(条件: プラットフォーム=Web、サーバー描画後にクライアントで動かす構成)〔必須〕
- フォーム内の送信以外のボタンが、押しただけでフォームを送信しないようにする(条件: プラットフォーム=Web)〔必須〕
- 見た目にかかわらず、操作を実行するものはボタン、別の場所へ移動するものはリンクとして実装する(条件: プラットフォーム=Web)
- モーダルやドロワーの中のスクロールが端に達しても、背後のページへスクロールを連鎖させない(条件: プラットフォーム=Web)
- 画像は寸法や縦横比を指定して表示領域を先に確保し、読み込み時に周囲をずらさない(条件: プラットフォーム=Web)
