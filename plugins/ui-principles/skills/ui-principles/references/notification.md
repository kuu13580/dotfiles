# 通知

読む場面: トースト・バナー・通知・状態メッセージを出すとき。条件がない原則はどこでも使い、条件がある原則は当てはまるときだけ使う。

## 原則

### 短時間で消える通知は重ねず、アクションを絞って文を短く保ち、操作中の要素を覆わず、機能への唯一の入口にしない〔推奨〕
条件: 機能=通知 ／ 理由: 重ねたり複雑にしたりすると軽い通知の役割を損ない、消える要素だけが入口だと機能に届かない。

### トーストで結果を知らせるときは、トーストが消えても結果の状態が分かるように画面上にも示す〔推奨〕
条件: 機能=通知、結果が操作した場所から見えない、または重要な操作でトーストを出すとき ／ 理由: 消えるトーストは見逃されやすい(結果が画面の変化や操作した場所で分かるなら出さない)。

### 1つの画面に同時に出す警告やバナーの数を抑え、警告色を多用しない〔推奨〕
理由: 警告だらけの画面は不安をあおり壊れて見える(複数なら重大度の高い順に並べる)。

### メッセージの割り込みの強さを重要度と緊急度に合わせ、作業を止めて判断が必要なものだけを作業を遮る形で出す〔推奨〕
理由: 強さが釣り合わないと重要な通知は見逃され、重要でない通知は作業を妨げる。
例: 状態の変化は対象の印、保存完了は短い通知、データを失いうる判断だけダイアログ。

### 成功の通知は、操作の結果が画面の変化から分からない場合や十分に重要な操作に限って出す〔推奨〕
理由: 結果がそのまま見えるなら通知はノイズで、知る必要があるのは主に失敗したとき。

## チェックリスト

- ユーザーの操作と関係のないタイミングで、作業を遮るダイアログや割り込みを出さない
- 時間のかかる処理を受け付けた時点では受け付けたことを伝え、完了したかのように書かない
- 成功メッセージは「成功しました」「正常に」で済ませず、何が完了したかを書く
