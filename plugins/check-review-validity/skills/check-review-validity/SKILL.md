# Check Review Validity

**submit ボタンを押す前の、自分のレビューに対するセルフレビュー。**

レビューで最もコストが高いのは、事実誤認の指摘に実装者が反論のための時間を使うことだ。「既に対応済みです」「そこは別の Observable です」と返させた時点で、そのコメントはレビュー全体の信頼を削っている。このスキルの仕事は、そういう指摘を **相手に届く前に** 見つけること。

したがって判定の重心は「文章として良いか」ではなく **「この指摘は事実として成立するか」** に置く。

## 引数

`$ARGUMENTS` を以下で解釈する (スクリプトが同じロジックでパースするので、そのまま渡せばよい):

- 空 → カレントブランチに対応する PR
- 正の整数 → カレントリポジトリのその PR 番号
- `https://github.com/<owner>/<repo>/pull/<N>` → その PR

## Step 1: ドラフトレビューの取得

```bash
bash ${CLAUDE_PLUGIN_ROOT}/skills/check-review-validity/scripts/fetch-pending-review.sh $ARGUMENTS
```

未 submit のドラフトは REST の `pulls/comments` には現れないため、スクリプトは GraphQL の `reviews(states: PENDING)` から取得する。pending review は本人にしか見えないので、取得できるのは常に自分のドラフトだけ。

### exit code の処理

| exit | 意味 | 対応 |
| ---- | ---- | ---- |
| 0 | ドラフト検出 (stdout に JSON) | Step 2 へ |
| 1 | エラー (依存不足 / 未認証 / API 失敗 / 引数不正) | stderr の内容をそのまま伝えて終了 |
| 3 | ドラフトレビューなし | 「PR #N に未 submit のドラフトレビューはありません」と伝えて終了。無理に別の対象を探しに行かない |
| 4 | カレントブランチから PR を特定できない | stderr の案内 (PR 番号/URL 指定) をそのまま伝えて終了 |

### JSON の主なフィールド

- `pending_review.comments[]`: 検証対象。`path` / `line` / `body` / `diff_hunk` / `outdated`
- `pending_review.body`: レビュー全体コメント (行コメントとは別に検証対象)
- `pr.body`: PR description。軸 3 で使う
- `submitted_reviews[]` / `other_threads[]`: 既に submit 済みのレビューとスレッド。重複検出に使う。
  GitHub の `reviewThreads` は自分の未 submit コメントも返してくるが、スクリプト側で ID 照合して除外済み。
  つまり `other_threads[]` に同じ指摘があれば **本当の重複** なので、そのまま重複と判断してよい
- `local_code_available`: ローカルに PR のコードがあるか (Step 2 の分岐)
- `dirty_worktree`: 未コミット変更の有無

## Step 2: 判定材料をそろえる

### コードの読み方 (`local_code_available` で分岐)

- **`true`** (カレントブランチ = PR の head): 各コメントの `path` を **Read でファイル全体** 読む。
  `diff_hunk` だけで判断してはいけない。ドラフト指摘が的を外す最大の原因は「差分の数行しか見ずに書いた」ことであり、同じ誤りを検証側で繰り返せばこのスキルは何も検出できない。
- **`false`** (引数指定でブランチ不一致、または別リポジトリ): 実ファイルがないので差分で判定する。

  ```bash
  gh pr diff <number> --repo <target_repository>
  ```

  この場合「別ファイルで既に手当て済み」の検証ができないため、レポート冒頭に必ず明記する:
  「⚠ ローカルに PR のコードがないため diff ベースの判定です (`gh pr checkout <N>` 後の再実行でより正確になります)」

### 規約ファイルの確認

指摘がプロジェクトの決めごとと衝突していないか見るため、対象リポジトリ内で以下を探す (Glob/Grep):

- `CLAUDE.md`、`.claude/rules/*.md`、`.cursorrules` 等の規約文書
- `eslint.config.*` / `.eslintrc*`、`tsconfig.json`、`.editorconfig`、`.prettierrc*`
- 同ディレクトリの類似ファイル (既存パターンの実地確認。規約文書に書かれていない慣習はコードにしか現れない)

`same_repository: false` のときはこれらが読めない。その旨をレポートに書き、規約軸の判定を保留する。

### 未コミット変更

`dirty_worktree: true` なら、読んだファイルが PR の内容と一致しない可能性がある。レポート冒頭に注意書きを 1 行出す。read-only なので処理はブロックしない。

## Step 3: 各ドラフト指摘を 4 軸 + 外部事実で検証

`pending_review.comments[]` と `pending_review.body` の全件について、以下を順に当てる。1 つでも該当したら判定が決まるので、上から順に見るのが速い。

### 軸 1: 事実正しさ (最優先)

- **既に手当て済みでないか**: 指摘した関数・シンボル・パターンを Grep で追い、同ファイルの別の場所や関連ファイルで既に対処されていないか確認する。
- **誤読していないか**: 該当行の前後、呼び出し元、型定義を読む。「この変数は null になり得る」型の指摘は、実際に null が入る経路があるか辿って確かめる。
- **PR の変更範囲外でないか**: `diff_hunk` を見て、指摘対象が追加・変更行 (`+`) ではなく既存行 (` `) に向いているなら、その PR のスコープ外の指摘。→ ❌ 寄り。
  ただし **その変更によって顕在化した既存の問題** は正当な指摘なので、区別する。
- **`outdated: true` の場合**: コメントを付けた後に実装者が該当箇所を push で変更している。現在のコードを読み直し、指摘が今も成立するか確認する。成立しないなら ❌、成立するなら行位置がずれている旨をレポートに書く。

### 軸 2: プロジェクト規約との整合

- 指摘が規約文書・lint 設定に **反していないか** (規約が禁じているやり方を勧めていないか)
- 規約や既存パターンで **既に許容されているやり方を否定していないか** (「このリポジトリではこう書く」が確立しているなら、個人的好みの押し付けになる)

規約と衝突する指摘は、内容の良し悪しに関わらず ❌。規約の変更はレビューコメントではなく別の議論の場でやるべきこと。

### 軸 3: PR の文脈

- `pr.body` に「意図的」「既知」「別 PR で対応」と書かれていないか
- `submitted_reviews[]` / `other_threads[]` に **同じ指摘がないか**。既に誰かが (あるいは自分が) 出しているなら、新しいコメントではなく既存スレッドへの返信にすべき → ❌ (理由: 重複)
- `other_threads[]` で `is_resolved: true` のスレッドが同じ箇所を扱っていないか (一度決着した話を蒸し返していないか)

### 軸 4: 伝わり方

内容が正しい前提で、実装者が動けるかを見る:

- **根拠がない**: 「なぜ問題か」が書かれていない指摘は、実装者が判断できず往復が増える → ✏️
- **nit と blocking の混同**: 好みレベルの話が断定形で書かれていると、実装者は必須修正だと受け取る → ✏️ (`nit:` を付ける等の文面案を出す)
- **複数の指摘が 1 コメントに混在**: 片方だけ直されて終わる → ✏️ (分割を提案)
- **過剰要求**: その PR の範囲を超えるリファクタ要求 → ✏️ か ❌ (別 Issue 化の提案)

### 軸 5: 外部事実の裏取り (条件付き)

**コードと規約だけでは真偽が決まらない技術的主張** を含む指摘に限り、WebSearch / WebFetch で確認する。内部知識で断定すると、古い知識のまま実装者に誤りを届けることになる。

走らせる例:
- 「この API / オプションは非推奨」「バージョン X 以降で使える」
- 「この書き方はメモリリークする / 遅い」
- 「このライブラリはこう動く」
- 「セキュリティ上危険」

走らせない例 (検索しても答えが出ない):
- 命名、可読性、コード構成の好み
- このリポジトリ固有の設計判断

裏取りした指摘は、判定根拠として **ソース URL をレポートに記載する**。

## Step 4: ラベルを決める

| ラベル | 条件 | レポートに書くこと |
| ------ | ---- | ------------------ |
| ✅ 妥当 | 全軸クリア。そのまま submit してよい | 何を確認して妥当と判断したか (1 行) |
| ✏️ 要修正 | 指摘自体は正しいが、根拠不足・優先度の伝わり方・粒度に問題がある | **修正後の文面案** を必ず添える |
| ❌ 取り下げ推奨 | 事実誤認 / 既に対応済み / 規約と衝突 / 重複 / スコープ外 | なぜ成立しないかの根拠 (ファイルと行番号を挙げる) |
| ❓ 要確認 | 実装者の意図に依存し、コードを読んでも決着しない | 実装者に何を聞くべきかを具体的に書く |

**❓ を逃げ道にしないこと。** コードを読めば分かることは読んで断定する。❓ が妥当なのは「この分岐が必要かどうかは仕様側の前提に依存する」のように、リポジトリ内の情報では原理的に決まらない場合だけ。迷ったら Read と Grep をもう一段深くやってから判定する。

## Step 5: レポート出力

以下の形式で **ターミナルに出力するだけ**。ファイル保存もしない。

```
## PR #{number} {title} — ドラフト {N} 件
{url}

{⚠ 注意書き (該当時のみ: diff ベース判定 / 未コミット変更あり / 別リポジトリで規約未参照 / PR が OPEN でない)}

| # | 判定 | 場所 | 一言 |
|---|------|------|------|
| 1 | ❌ 取り下げ | {path}:{line} | {20 字程度の要点} |
| 2 | ✏️ 要修正 | {path}:{line} | {20 字程度の要点} |
| 3 | ✅ 妥当 | {path}:{line} | そのまま submit 可 |
| 4 | ❓ 要確認 | {path}:{line} | {20 字程度の要点} |

### [1] ❌ 取り下げ推奨 — {path}:{line}
> {ドラフト本文を引用}

{判定理由。根拠にしたファイル名と行番号を必ず含める}

### [2] ✏️ 要修正 — {path}:{line}
> {ドラフト本文を引用}

{判定理由}

**文面案**: 「{そのまま貼れる修正後の文面}」

---
補足 (見落とし候補): {1-3 件、なければこの行を省略}
サマリ: ✅ {n} / ✏️ {n} / ❌ {n} / ❓ {n}
```

### 出力の細部

- **詳細セクションの順序**: ❌ → ✏️ → ❓ → ✅。直すべきものを先に見せる。
- **件数が多いとき (目安 8 件超)**: ✅ は表に載せるだけで詳細セクションを省略する。判断が要るものに紙面を使う。
- **`pending_review.body`** (レビュー全体コメント) がある場合は、表の `#` を `body` として 1 行足し、詳細も同様に扱う。場所欄は `(レビュー本文)` とする。
- **補足 (見落とし候補)**: 検証のために diff を読んだついでに気づいた重大な問題だけ、最大 3 件。無理に埋めない。網羅的なレビューはこのスキルの仕事ではない (それは `/code-review` の領域)。
- **外部事実の裏取りをした指摘**: 判定理由の末尾にソース URL を付ける。

## 制約

- **GitHub への書き込みは一切しない。** `gh api` の POST/PATCH/DELETE、`gh pr comment`、`gh pr review`、ドラフトの編集・削除・submit はすべて禁止。このスキルの出力はレポートのみで、反映するかどうかはユーザーが GitHub UI で決める。
- **ドラフト本文を勝手に書き換えない。** ✏️ の文面案は提案として出すだけ。
- **`git checkout` しない。** ローカルにコードがなければ diff ベースに落とす (質問した上で checkout させるのではなく、精度限定を明記して続行する)。
- **判定基準は「実装者にとって有益か」。** 文章の綺麗さではなく、そのコメントが相手の時間を使う価値があるかで判断する。
- **自分のドラフトだけが対象。** 他人の pending review は API 上見えないので、混ざる心配はない。
