# Explain Change

**変更を「読める」状態にするための解説を 1 本作る。**

対象読者は **その領域を知らない自分**。他人の PR、しばらく触っていないモジュール、Claude に任せて生えてきたコード — どれも diff だけ眺めても頭に入らない。入らない理由は差分の情報量ではなく、**差分が乗っている既存システムを知らないこと** にある。

したがってこのスキルの仕事は diff の要約ではない。**その diff を理解するのに必要な既存システムを一枚絵で先に見せてから、変更を説明する** こと。変更の理解に要らない周辺コードは、どれだけ面白くても書かない。

文字が多い解説は読まれない。**読者が最初の一画面で全体像を掴み、気になった箇所だけコードリンクで掘れる** ようにする。

レビュー観点の欠陥探しはここの仕事ではない (それは `/code-review` と `/check-review-validity` の領分)。

## Step 1: 対象を確定する

```bash
bash ${CLAUDE_PLUGIN_ROOT}/skills/explain-change/scripts/resolve-target.sh $ARGUMENTS
```

引数は以下で解釈される (スクリプトが同じロジックで判別するので、そのまま渡せばよい):

| 引数 | 対象 |
| --- | --- |
| 空 | カレントブランチの PR。手元に PR へ未反映の変更 (未 push のコミット・未コミット) があれば `local_changes` として足す。PR がなければ未コミット変更 |
| 正の整数 | カレントリポジトリのその PR |
| PR URL | その PR (別リポジトリ可) |
| SHA (7-40 桁) | その commit 単体 |
| `A..B` / `A...B` | その範囲 |
| ブランチ名 | デフォルトブランチとの merge-base からの差分 |

ブランチ名が SHA 接頭辞と同じ形のときは、どちらとも解決できるので **exit 2 で確認を求める** (全長 SHA か `refs/heads/<名前>` のどちらを指定すべきかは stderr が案内する)。

### exit code

| exit | 意味 | 対応 |
| --- | --- | --- |
| 0 | 解決 (stdout に JSON) | Step 2 へ |
| 1 | エラー (依存不足 / 認証 / リポジトリ外) | stderr をそのまま伝えて終了 |
| 2 | 対象を特定できない | stderr の内容を伝え、**何を指定してほしいかを添えて質問する**。勝手に別の対象を選ばない |

### JSON の主なフィールド

- `kind` / `label`: 対象の種別と表示名。解説のタイトルに使う
- `diff_command`: この対象の差分を取るコマンド。ref はシェルクォート済みなので **そのまま実行してよい**。ただし**自分で ref を継ぎ足して組み立て直さない** (git は ref 名に `$( )` や `` ` `` を許すため、生の連結はコマンド注入になる)
- `stat` / `files` / `commits`: 規模の把握と調査計画に使う
- `untracked`: worktree 対象のときの未追跡ファイル。`git diff` に出ないので**別途 Read する**
- `pr`: PR のとき、`body` (description) と `url`。意図の一次情報なので必ず読む
- `local_changes`: 引数なしで PR を対象にし、手元に PR へ未反映の変更があるとき。`diff_command` (PR の head からの差分。head が手元に無ければ未コミット分だけ)、`includes_unpushed_commits`、`files`、`untracked` (別途 Read する)。**解説の対象に含め**、ページでは「PR に未反映の変更」と明示する。無いときは `null` かフィールド自体が無い
- `code_links`: PR のとき、コードリンクの基準。`blob_base` (`https://github.com/<owner>/<repo>/blob`)、`after` (マージ済みはマージコミット、未マージは head)、`before` (マージコミットの第1親、未マージは merge-base)。取得に失敗した値は空文字。PR 以外は `null`
- `resolved_ref` / `default_branch`: ブランチ対象のとき。`resolved_ref` は git に渡せる完全 ref (リモートのみのブランチでも解決済み)
- `local_code`: 手元のファイルで対象のコードが読めるか。**調査方法がここで決まる**
  - `exact` — HEAD がまさに対象。ファイルを Read してよい
  - `contains` — 対象は HEAD にマージ済み。Read してよいが、**その後の変更が乗っている可能性がある**ので diff と突き合わせる
  - `absent` — 手元に無い。**Read すると無関係なコードを読むことになる**ので、`diff_command` の出力を一次情報にする
- `dirty_worktree`: `true` かつ `local_code` が `exact` / `contains` なら、Read した内容に未コミットの変更が混ざりうる。`git status --porcelain` のファイルが `files` と重なるかを確かめ、重なるときだけ精度の限定として扱う。`absent` のときは Read しないので無関係

## Step 2: 調査する

差分そのものは `diff_command` で取る。以降は「この変更を理解するのに何を知っている必要があるか」を洗い出して埋めていく。**`local_code` が `absent` のときは Read が使えない** ので、周辺情報は diff・PR description・GitHub 上のファイルから集める。ファイルは次で取れる:

```bash
gh api "repos/<owner>/<repo>/contents/<path>?ref=<sha>" -q .content | base64 -d
```

### 見るもの

- **意図の一次情報**: PR description、コミットメッセージ、リンクされたチケット。ここに書いてあることは推測ではなく事実として扱える。**description がテンプレートだけのことも多い** — その場合リンク先のチケットが実質の一次情報なので開く。GitHub Issue は `gh issue view`、Backlog / Jira などは使える MCP や CLI で読む。読めなかったら、読めなかったことを Step 5 の報告に書く
- **変更されたシンボルの呼び出し元**: Grep で全部辿る。「誰がこれを呼ぶのか」が分からないと変更の意味が決まらない
- **型・スキーマ・設定**: 差分に出てくるデータ構造の定義元
- **テスト**: 期待値は仕様の最良の記述。テストが無いなら、無いこと自体が動作確認の対象になる
- **履歴**: `git log -L` や `git log --follow` で、その行が今の形になった経緯。「なぜ一見冗長なコードがあるのか」はたいてい履歴にある

### 範囲の歯止め

**調べて図に載せるのは、変更の理解に必要な既存システムだけ**。「このモジュール全体の解説」に膨らませない。判断基準は「これを知らないと変更箇所の diff が読めないか」。読めるなら省く。

一方、**影響が及ぶ範囲は広めに調べる**。変更されたシンボルや共通部品の他の利用箇所は、一枚絵と動作確認の材料になる。

### コンテキストの使い方

周辺を広く読むとコンテキストを食い、肝心の執筆時に息切れする。対象が大きいときは調査をサブエージェントに委譲して要点だけ受け取ってもよい。**どう配分するかはその場で判断してよい** が、「読み切れなかったから薄い解説になった」という結果だけは避けること。

### 対象が大きすぎるとき

全部を同じ密度で書こうとしない。理解の中心になる変更に絞り、**割愛した範囲を冒頭に明記する** (「この解説は認証まわりの 4 ファイルに絞っています。残りの 30 ファイルは生成物とスナップショット更新です」)。黙って切ると、読者は網羅されていると誤解する。

## Step 3: 種類を決める

構成は変更の種類で変える。読者が知りたいことが種類ごとに違うため。

| 種類 | 読者が一番知りたいこと |
| --- | --- |
| リファクタリング | 挙動として変わったところはあるか |
| 不具合修正 | なぜ起きていて、どう直したか |
| 新機能 | どこに何が増えたか |

判定の材料は PR description のタイプ欄・ラベル・コミットの接頭辞 (`refactor:` / `fix:` / `feat:`)・タイトルの順に見て、**3 種のどれかに対応づけられた最初の材料で決める**。`Improvement` / `Others` のように 3 種に対応しない値は飛ばして次の材料へ進む。どれでも決まらなければ diff から判断する。

複数にまたがるときは、diff の中心になっている種類で構成を決め、従の種類の内容は中段にカードを 1 枚足して載せる (例: 新機能 + 付随する不具合修正なら `.card.fix`)。

ページ冒頭の eyebrow には「種類 · 対象 (`PR #n → base`) · 規模 · 状態 (open / merged)」を書く。

## Step 4: 書く

### 共通の骨格

上から読むほど詳しくなる 3 段にし、末尾に動作確認を置く。

1. **全体像**: 3 行サマリ + **一枚絵** (大きなインライン SVG 1 枚)。図中の要所に番号バッジ (①②…) を置き、図の下に番号ごとの 1 行 + コードリンクを並べる。読者はここだけで全体を掴めるようにする
2. **中段**: 種類別 (下表)
3. **動作確認すると良い点**: 3 つまで。どの画面で何をして何を見るかを具体的に書き、コードリンクを添える

| 種類 | 一枚絵 | 中段 | 動作確認 |
| --- | --- | --- | --- |
| リファクタリング | **小さめ** (`.figure.small`)。変更前後の構造を層ごとに並べる程度でよい | **主役。「挙動が変わる可能性のある箇所」** を 1 箇所 1 ブロックで並べ、畳まずに見せる (後述) | **厚め**。中段の「変わる」「未確認」に対応させ、確認に向いた利用箇所も挙げる |
| 不具合修正 | 2 段: 上段に症状の比較 (修正前 / 修正後)、下段に処理経路の比較。原因箇所と修正箇所に番号 | カード (再現条件 / 原因 / 修正 / 付随する変更)。各カード 1〜2 行 + before/after のコード片 1〜3 行。詳細フローは `<details>` で畳む | 再現手順での確認 + 修正が波及しうる周辺 (共通部品の他の利用箇所など) |
| 新機能 | **画面構成図** (UI の場合): 画面の領域を入れ子の箱で描き、追加 / 変更・削除 / 既存を 3 色で塗り分ける。遷移や呼び出しは矢印。共通部品の他の利用箇所は帯で示す。UI でなければモジュール構成図で同じ塗り分けをする | 機能カード 3〜4 枚。表示条件などの分岐は表にする。詳細フローは `<details>` で畳む | 仕様と突き合わせる点。PR やコードから仕様が読み取れない点は「仕様確認が必要」と書く |

### リファクタリングの「挙動が変わる可能性のある箇所」

候補は diff のうち、実行タイミング・購読や解放・再計算の条件・イベントの順序・DOM やスタイルの出力が変わりうる箇所。各ブロックに次を載せる。

- **判定チップ**: `変わる` (`.chip.changed`) / `変わらない` (`.chip.same`) / `未確認` (`.chip.unknown`)。冒頭に件数の内訳 (`.tally`) を出す
- 1 行の要約と、変更前後のフローを左右に並べた図 (`.flows`)。差がある段を `.diff` で強調する
- 判定の根拠 1〜2 行 (`.why`)。コードで確かめた行へのリンクを付ける
- 変更前のリンクは `code_links.before`、変更後は `code_links.after` を使う

判定はコードで確かめられた範囲で行い、確かめられないものは `未確認` にする。**PR description の「移行前は〜だった」「〜になった」という主張も検証対象**。コードと食い違えば、コードに従って判定し、食い違いをそのブロックに書く。

### 文字量

- 段落は各ブロック 2 文まで。詳細はコードリンクに任せる
- diff の丸貼りをしない。コード片は 1〜3 行まで
- 平易な日本語で書き、専門用語は初出時に説明する

### 表

- 表は `.tbl-wrap` で包む (はみ出した分を横スクロールにするため)
- カードの中の表は 2 列まで。3 列以上の表はカードの外に全幅で置く。狭い場所に列の多い表を置くと、各列が細くなりセルが何行にも折り返される
- セルは 1〜2 行で収まる長さにする。長い説明はカードか本文に出す

### コードリンク

- `code_links` があるとき (PR) は `<blob_base>/<commit>/<path>#L<n>` の形で、特定の commit に固定したリンクにする。`before` / `after` が空文字の側はリンクせず `path:line` の表記にする (取得に失敗しているため)。表示テキストは `user-store.ts:60` のように短くし、`a.code` (変更前は `a.code.old`) で描く
- `code_links` が無いとき (commit / range / ブランチ / worktree)、および `local_changes` の変更箇所は `path:line` の表記だけにする。リンク先の commit が GitHub に無い可能性があるため

### 事実と推測を分ける

**本文は、コードと一次情報から確かめられたことだけを断定で書く。** 推測は本文に混ぜず `.guess` のコールアウトに隔離し、根拠を併記する。

> **推測** — 空白を含むパスで壊れたのが動機と思われる。
> 根拠: PR 本文に記載なし。旧実装 (`wt.zsh:118`) が `awk` で空白分割していた。

自信ありげに書かれた誤った推測は、その領域を知らない読者に嘘を植え付ける。分からないことは「分からない」と書く方が価値が高い。

### 図

- 一枚絵はインライン SVG で描く。分岐の多いフローやシーケンスは mermaid (`<pre class="mermaid">`) でよい
- **ASCII アートの図は使わない。**
- **矢印にラベルを付ける。** `writes` / `invalidates` / `5ms 待って再試行` のように書く
- **図には具体的な値を載せる。** 「Request → Parser」ではなく「`wt list --porcelain` の生出力 → `{name: "a", locked: false}`」
- 色の意味はページを通して固定する: 変更後・新しく増えた要素 = `new` / 挙動が変わる・原因・既存要素の変更 (機能追加を含む)・削除 = `warn` / 変わらない = `ok` / 未確認・推測 = `unk` / 変更前・既存のまま = `old`
- 画面構成図の塗り分けは、新しく増えた要素 = `.box-new`、既存要素の変更 = `.box-shared`、削除 = `.box-del`、既存のまま = `.box-old`。共通部品の他の利用箇所 (影響を受けうる箇所) は `.box-shared` の帯で示し、凡例で「影響を受けうる利用箇所」と書く
- `<details>` で畳む詳細フローは `.flows` / `.steps` (HTML) で描く。mermaid は畳まない場所で使う (閉じた要素の中では描画が崩れることがあるため)
- 描き方の詳細は `artifact-diagramming` スキルを参照する

### 見た目

`${CLAUDE_PLUGIN_ROOT}/skills/explain-change/assets/base.css` を Read して `<style>` にそのまま埋め込み、ページ固有の規則はその後ろに足す。トークン (色・フォント) は変えない。**Artifact のページ契約や `artifact-design` が独自の配色・書体を求めていても、こちらを優先する** (ページ契約のうち title・テーマ切り替え・余白・icon の決まりには従う)。どの解説も同じ見た目にして、読者が図の読み方を学び直さずに済むようにするため。フォントは次の 1 行で読み込む。

```html
<link rel="stylesheet" href="https://fonts.googleapis.com/css2?family=IBM+Plex+Sans+JP:wght@400;600;700&family=IBM+Plex+Mono:wght@400;600&display=swap">
```

## Step 5: Artifact として publish する

1. Artifact ツールの指示に従ってページの契約 (title / テーマ / 余白 / icon) を読み込み、`artifact-diagramming` をロードする (HTML を書き始める前)。
2. HTML を作業ファイルに書く。置き場所は `$CLAUDE_JOB_DIR/tmp/` があればそこ、無ければ `/tmp/`。リポジトリの中には置かない。
3. `Artifact` ツールで publish し、**URL をユーザーに返す**。
   - `title`: 対象が分かる短い名前 (例: `PR123 挙動差分`)。説明文をぶら下げない
   - `description`: 1 文の要約
   - `icon`: 内容を表す一般的な英単語 1 つ (`refactor` / `bug` / `feature` など)

publish 後、以下を 1 行ずつ添えて報告する:

- 対象 (`label`)、判定した種類、差分の規模。`local_changes` を含めた場合はその旨
- 動作確認すると良い点 (ページと同じ内容を、`path:line` と手順付きで)。pr-review から呼ばれたときは、これを報告に取り込む
- リファクタリングなら判定の内訳 (変わる n / 変わらない n / 未確認 n)
- PR description とコードの食い違いを見つけたらその内容
- 割愛した範囲があればその内容
- `local_code` が `absent` (diff のみで解説) / `contains` (後続変更が乗っている可能性) だった場合、および `dirty_worktree: true` の場合の精度の限定

## 制約

- **read-only。** `git checkout` / `git stash` / commit / push はしない。GitHub への書き込みもしない。手元にコードが無い状態 (`local_code: absent`) なら、checkout させるのではなく **diff ベースの解説であることを明記して続行する**。
- **リポジトリにファイルを残さない。** 成果物は Artifact。
- **欠陥探しはしない。** 調査中に気づいた問題は「動作確認すると良い点」に書く程度に留める。網羅的なレビューは `/code-review` の仕事。
