# Explain Change

**変更を「読める」状態にするための解説を 1 本作る。**

対象読者は **その領域を知らない自分**。他人の PR、しばらく触っていないモジュール、Claude に任せて生えてきたコード — どれも diff だけ眺めても頭に入らない。入らない理由は差分の情報量ではなく、**差分が乗っている既存システムを知らないこと** にある。

したがってこのスキルの仕事は diff の要約ではない。**その diff を理解するのに必要な既存システムを先に立ち上げてから、変更を説明する** こと。逆に言えば、変更の理解に要らない周辺コードは、どれだけ面白くても書かない。

レビュー観点の欠陥探しはここの仕事ではない (それは `/code-review` と `/check-review-validity` の領分)。

## Step 1: 対象を確定する

```bash
bash ${CLAUDE_PLUGIN_ROOT}/skills/explain-change/scripts/resolve-target.sh $ARGUMENTS
```

引数は以下で解釈される (スクリプトが同じロジックで判別するので、そのまま渡せばよい):

| 引数 | 対象 |
| --- | --- |
| 空 | 未コミット変更があればそれ。なければカレントブランチの PR |
| 正の整数 | カレントリポジトリのその PR |
| PR URL | その PR (別リポジトリ可) |
| SHA (7-40 桁) | その commit 単体 |
| `A..B` / `A...B` | その範囲 |
| ブランチ名 | デフォルトブランチとの merge-base からの差分 |

### exit code

| exit | 意味 | 対応 |
| --- | --- | --- |
| 0 | 解決 (stdout に JSON) | Step 2 へ |
| 1 | エラー (依存不足 / 認証 / リポジトリ外) | stderr をそのまま伝えて終了 |
| 2 | 対象を特定できない | stderr の内容を伝え、**何を指定してほしいかを添えて質問する**。勝手に別の対象を選ばない |

### JSON の主なフィールド

- `kind` / `label`: 対象の種別と表示名。解説のタイトルに使う
- `diff_command`: この対象の差分を取るコマンド。**そのまま実行してよい**
- `stat` / `files` / `commits`: 規模の把握と調査計画に使う
- `untracked`: worktree 対象のときの未追跡ファイル。`git diff` に出ないので**別途 Read する**
- `pr`: PR のとき、`body` (description) と `url`。意図の一次情報なので必ず読む
- `resolved_ref` / `default_branch`: ブランチ対象のとき。`resolved_ref` は git に渡せる完全 ref (リモートのみのブランチでも解決済み)
- `local_code`: 手元のファイルで対象のコードが読めるか。**調査方法がここで決まる**
  - `exact` — HEAD がまさに対象。ファイルを Read してよい
  - `contains` — 対象は HEAD にマージ済み。Read してよいが、**その後の変更が乗っている可能性がある**ので diff と突き合わせる
  - `absent` — 手元に無い。**Read すると無関係なコードを読むことになる**ので、`diff_command` の出力を一次情報にする
- `dirty_worktree`: `true` かつ `local_code` が `exact` / `contains` なら、Read した内容に未コミットの変更が混ざる。`absent` のときは Read しないので無関係

## Step 2: 調査する

差分そのものは `diff_command` で取る。以降は「この変更を理解するのに何を知っている必要があるか」を洗い出して埋めていく。**`local_code` が `absent` のときは Read が使えない** ので、周辺情報は diff・PR description・GitHub 上のファイルから集める。ファイルは次で取れる:

```bash
gh api "repos/<owner>/<repo>/contents/<path>?ref=<sha>" -q .content | base64 -d
```

### 見るもの

- **意図の一次情報**: PR description、コミットメッセージ、リンクされた Issue。ここに書いてあることは推測ではなく事実として扱える。**description がテンプレートだけのことも多い** — その場合 `Fix #123` のリンク先 Issue が実質の一次情報なので、必ず `gh issue view` で開く
- **変更されたシンボルの呼び出し元**: Grep で全部辿る。「誰がこれを呼ぶのか」が分からないと変更の意味が決まらない
- **型・スキーマ・設定**: 差分に出てくるデータ構造の定義元
- **テスト**: 期待値は仕様の最良の記述。テストが無いなら、無いこと自体が押さえどころになる
- **履歴**: `git log -L` や `git log --follow` で、その行が今の形になった経緯。「なぜ一見冗長なコードがあるのか」はたいてい履歴にある

### 範囲の歯止め

背景章に紙幅を割く (**目安として解説全体の 3-4 割**。それより薄いなら読者モデルを外している) が、**書くのは変更の理解に必要な既存システムだけ**。「このモジュール全体の解説」に膨らませない。判断基準は「これを知らないと変更箇所の diff が読めないか」。読めるなら省く。

### コンテキストの使い方

周辺を広く読むとコンテキストを食い、肝心の執筆時に息切れする。対象が大きいときは調査をサブエージェントに委譲して要点だけ受け取ってもよい。**どう配分するかはその場で判断してよい** が、「読み切れなかったから薄い解説になった」という結果だけは避けること。

### 対象が大きすぎるとき

全部を同じ密度で書こうとしない。理解の中心になる変更に絞り、**割愛した範囲を冒頭に明記する** (「この解説は認証まわりの 4 ファイルに絞っています。残りの 30 ファイルは生成物とスナップショット更新です」)。黙って切ると、読者は網羅されていると誤解する。

## Step 3: 書く

### 章構成

1. **この変更は何か** — 3 行サマリ。ここだけ読んで人に説明できる粒度
2. **背景** — 初見向けの全体像から入り、変更箇所周辺の具体的な契約まで降りる。既に詳しい読者が飛ばせるよう、前半は畳めるようにしておく
3. **直感** — 何がどう変わったかの核心。トイデータと before/after で、実装詳細に入る前に絵を渡す
4. **コードの歩き方** — 実行順・依存順にグルーピングして説明する。ファイル順に並べない。`file:line` を添えて実物に飛べるようにする。diff の全文は貼らない
5. **押さえどころ** — 影響範囲 / 落とし穴 / 未解決の痛み。「で、これを知ったあと何に気をつければいいのか」に答えて終わる

### 事実と推測を分ける

**本文は、コードと一次情報から確かめられたことだけを断定で書く。** 動機や設計意図が明記されていないときの推測は、本文に混ぜず専用のコールアウトに隔離し、根拠を併記する。

> **推測** — 空白を含むパスで壊れたのが動機と思われる。
> 根拠: PR 本文に記載なし。旧実装 (`wt.zsh:118`) が `awk` で空白分割していた。

自信ありげに書かれた誤った推測は、その領域を知らない読者に嘘を植え付ける。分からないことは「分からない」と書く方が価値が高い。

### 図

**図は多めに。** 各章に最低 1 枚、章の主張が「機構」であれば必ず図にする。書き終えたら章ごとに一度 **「この段落は図にできないか」** を問い直す。散文で説明しきれてしまうものほど、図にすると読者の時間が縮む。

| 章 | 定番の図 |
| --- | --- |
| 背景 | 変更前の構造。登場人物と、その間を流れるデータ |
| 直感 | before / after の対比。具体値を載せたタイムラインや状態遷移 |
| コードの歩き方 | 関数間の呼び出しと分岐。**追加された経路が一目で分かる**フロー |
| 押さえどころ | 境界値、失敗経路、分岐の一覧 |

道具は 3 つ。**型を 3-4 種に絞り、同じ見た目を使い回す** (毎回違う描き方をすると、読者は図の読み方から学び直すことになる)。

| 使うもの | 用途 | 備考 |
| --- | --- | --- |
| インライン SVG | 機構そのもの。データの流れ、境界、追加・削除された経路 | `currentColor` で描けば両テーマで成立する。**第一候補** |
| mermaid | 分岐の多い制御フロー、依存グラフ、シーケンス、状態遷移 | 座標を手で置くのが割に合わないグラフ構造のとき |
| HTML + CSS | before/after の 2 カラム、バイト列などの整列、契約・不変条件の表 | テキストの整列そのものが主役のとき |

- **ASCII アートの図は使わない。**
- **矢印にラベルを付ける。** 無印の矢印は「何か関係がある」以上を伝えない。`writes` / `invalidates` / `5ms 待って再試行` と書く。
- **図には具体的な値を載せる。** 「Request → Parser → Store」ではなく「`wt list --porcelain` の生出力 → `worktree /path/to/a` 行 → `{name: "a", locked: false}`」。
- **1 枚の図に 1 つの主張。** `<figure>` + `<figcaption>` で何を示した図かを書き、SVG には `role="img"` と `aria-label` を付ける。
- 描き方の詳細は `artifact-diagramming` スキルを参照する。

### 文体

- 平易な日本語。専門用語は初出時に説明する
- 章から章へ流れるように書く。箇条書きの羅列で済ませない
- コードブロックは `<pre><code>` を使い、CSS に `white-space: pre` か `pre-wrap` を必ず入れる (無いと改行が潰れる)

## Step 4: Artifact として publish する

1. **`artifact-design` と `artifact-diagramming` を先にロードする** (HTML を書き始める前)。
2. HTML を作業ファイルに書く。置き場所は `$CLAUDE_JOB_DIR/tmp/` があればそこ、無ければ `/tmp/`。リポジトリの中には置かない。
3. `Artifact` ツールで publish し、**URL をユーザーに返す**。
   - `title`: 対象が分かる短い名前 (例: `wt locked 判定の porcelain 化`)。説明文をぶら下げない
   - `description`: 1 文の要約
   - `favicon`: 絵文字 1-2 個

publish 後、以下を 1 行ずつ添えて報告する:

- 対象 (`label`) と差分の規模
- 割愛した範囲があればその内容
- `local_code` が `absent` (diff のみで解説) / `contains` (後続変更が乗っている可能性) だった場合、および `dirty_worktree: true` の場合の精度の限定

## 制約

- **read-only。** `git checkout` / `git stash` / commit / push はしない。GitHub への書き込みもしない。手元にコードが無い状態 (`local_code: absent`) なら、checkout させるのではなく **diff ベースの解説であることを明記して続行する**。
- **リポジトリにファイルを残さない。** 成果物は Artifact。
- **欠陥探しはしない。** 調査中に気づいた問題は「押さえどころ」に落とし穴として書く程度に留める。網羅的なレビューは `/code-review` の仕事。
- **diff の丸貼りをしない。** 解説になっていない引用は、読者が diff を直接見るのと同じ。
