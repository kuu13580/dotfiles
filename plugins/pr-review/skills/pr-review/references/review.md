# フェーズA: レビューを作る

(理解) → 洗い出し → 重複除去 → 分類 → 検証 → 投稿 → 報告。

投稿に残るのは **検証で裏が取れた指摘だけ**。ここを緩めると、実装者が反論に使う時間が増えてレビュー全体の価値が下がる。

## A-0. 先に変更を理解する (`--explain` 指定時のみ)

指摘の質は、その変更が何をしようとしているかを分かっているかで決まる。知らない領域の PR では、解説を先に読んでから指摘を見る方が速い。

`--explain` があれば、洗い出しの前に Skill ツールで `explain-change` を呼ぶ (引数は PR 番号)。Artifact の URL をユーザーに渡してから A-1 に進む。

`explain-change` が無い環境では、変更の要点をターミナルに 5 行以内で出すだけにする。Artifact を作るために別の仕組みを立てない。

## A-1. 洗い出す (3 系統を並行で)

**系統1: `/code-review`**

Skill ツールで `code-review` を呼ぶ。引数は `<level> <PR番号>` (level は既定 `high`)。

`--comment` と `--fix` は **絶対に付けない**。前者は GitHub に直接コメントを投げ、後者はコードを書き換えてしまう。このスキルは検証を通してから自分で投稿する。

`high` を既定にしているのは、この後の検証フィルタで落とす前提だから。洗い出し段階で絞ると、検証すれば成立したはずの問題まで消える。

**系統2: 規約パス (Agent で並行)**

`/code-review` も規約違反を拾ってくるが、リポジトリ固有の細かい決めごとは取りこぼす。`fetch-pr-context.sh` の `rule_files` を渡して専用に走らせる:

```
対象: <repo> の PR #<N> の差分 (gh pr diff <N> で取得)
規約ファイル: <rule_files のうち変更ファイルに関係するもの>

これらの規約ファイルを読み、PR の差分が違反している箇所だけを挙げてください。
各項目に必ず「規約ファイル:行番号」と、その行の原文引用を付けてください。
引用できないもの (規約に書かれていない好み・一般論) は挙げないでください。
変更行に対する違反のみ。既存行は対象外です。
```

**系統3: 仕様・設計パス (Agent で並行)**

系統1・2 はどちらも「コードベースの中で正しいか」を見る。だが実際のレビューで効くのは、**コードベースの中では筋が通っているのに、仕様や設計として引っかかる**ところだ。この系統だけは「コードを読めば答えが出ること」を探さない。**実装者に聞かないと決まらないこと**を探す。

PR の説明に仕様書やチケットの URL があり、手元のツールで読めるなら読む。読めなければ参照不可として進め、レポートにその旨を添える (読めた前提で書くと、書かれていない要件を勝手に補ってしまう)。

```
対象: <repo> の PR #<N> (gh pr diff <N> の差分と、周辺の既存コード)
PR の説明: <pr.body>
仕様書: <読めた場合はその内容 / 読めなければ「参照不可」>

コードから読み取れる「実装された仕様」に対して、レビュアーが確認しておいた方がよい点を
次の 4 観点で挙げてください。

1. [妥当性] コードからはこう実装されていると読めるが、事業・運用・アーキテクチャの観点で
   それを決めてよいのかが別途判断を要するもの。
   例: 失敗時に自動リトライするが、副作用のある操作で二重実行にならないか /
       制限値がハードコードだが、利用プランや契約で変わる類の値ではないか
2. [要件担保] 仕様書・PR の説明に書かれた要件のうち、壊れたら影響が大きいものが
   実装で本当に閉じているか。「書かれているから通す」ではなく、重要なものは
   レビュアーが目を通す対象として挙げる。仕様書が参照不可なら PR の説明の範囲で判断し、
   その限界を明記する。
3. [エッジ] 仕様書にも実装にも扱いが現れていない入力・状態。
   空 / 0 件 / 1 件 / 上限超過 / 境界値 / 同時実行 / 権限なし / 通信断 / 途中失敗。
   「考慮した結果こうしている」のか「考慮されていない」のかが差分から読み取れないもの。
4. [アーキ] 責務の置き場所が既存の層構成と合っているか / 既存の抽象と重複していないか /
   依存の向き / 状態の持ち方 / 次に似た機能が来たとき破綻しないか。

出力の決まり:
- **影響の大きさ × 実装者に聞かないと決まらない度合い** の順に並べる
- 上位 3 件は 4 行: `[観点] 気になる点` / なぜコードだけでは決まらないか / 何を確認すれば決まるか
- 4 件目以降は 1 行サマリのみ (最大 5 件)。合計 8 件を超えない
- 同じ趣旨のものは束ねて 1 件にする
- コードを読めば答えが出るもの (= 単なる不具合) はここに入れない
```

件数を絞るのは、ここが膨らむと投稿分の指摘まで埋もれるから。一方で PR が大きいと 3 件では取りこぼすので、**詳細は上位 3 件に抑え、残りは 1 行で並べる**形にしてある。ユーザーが「4 番を詳しく」と言えばそこだけ掘る。

## A-2. 重複を除く

`existing_threads` (他レビュアー・bot の既存スレッド) と突き合わせ、**同じ箇所の同じ趣旨**は落とす。既に出ている指摘を別スレッドで立て直すと、実装者は同じ話に 2 回答えることになる。

`is_resolved: true` のスレッドが同じ箇所を扱っている場合も落とす。一度決着した話の蒸し返しになる。ただし解決時の修正が今のコードで戻っている (再発している) なら落とさず、再発した commit を本文に示して出す。

落とした件数と、誰の指摘と重複したかはターミナル報告に残す。

## A-3. 分類する

各指摘を次で仕分ける。判断に主観を入れないため、**順に当てる**:

| 判定 | 条件 | 行き先 |
| --- | --- | --- |
| 【規約】 | `rule_files` のいずれかの行を引用して「これに反している」と言える | 投稿 |
| 【不具合】 | 引用できないが、壊れる経路がある (A-4 で検証する) | 検証を通れば投稿 |
| 【確認】 | 系統3 由来。コードを読んでも真偽が決まらず、仕様・設計 (妥当性 / 要件担保 / エッジ / アーキ) の判断が要る | レポート (既定では投稿しない) |
| 落とす | 上のどれでもない (命名の好み、分割の提案、一般論のベストプラクティス) | — |

「規約に書いてある気がする」で【規約】にしない。**実際にファイルを開いて行を特定する**。特定できなければ【不具合】側で扱い、壊れる経路を示せなければ落とす。

【確認】を投稿しないのは、検証で裏が取れないものを断定形で送ると実装者が反論に時間を使うから。ただし **判断を仰ぐ問いとしては価値がある**ので、A-8 でユーザーに選ばせ、選ばれたものだけ `【確認】` タグを付けて pending に加える。

系統1・2 の指摘が実は【確認】だった場合 (壊れる経路を示せず、規約も引用できないが、仕様として引っかかる) は【確認】に移す。落とすより、ユーザーの判断に回す方がよい。

## A-4. 検証する

**【不具合】は全件、以下の順で裏を取る。**

**(1) テストで再現できるか試す。** これが第一手段。

- 対象ファイルの隣に `<name>.review-check.spec.ts` のような、後で自分が消せると分かる名前で書く
- テストランナーは対象リポジトリの設定から判断する (`package.json` の scripts、`vitest.config.*` / `jest.config.*` / `karma.conf.*` など)
- **そのファイルだけ**を指定して実行する。スイート全体を走らせると時間を食う
- 結果を控えたら **自分が作ったファイルだけ削除する**。他の未コミット変更には触れない
- 依存が入っておらずテストが動かない場合は、インストールに時間がかかることを伝えて判断を仰ぐ (黙って `npm ci` を始めない)

再現したら【検証済み】。再現しなかったら、コードを追って理由を確定させる (guard が上流にある / 型定義上その値にならない 等)。理由まで書けたら **不成立として落とす**。

**(2) テストで再現できないものは、コードを追って到達経路を確定させる。** 呼び出し元・型定義・分岐を実際に読む。経路が書けたら【検証済み】、書けなければ (3) へ。

**(3) 実機でしか分からないもの (UI の崩れ、タイミング、デバイス依存) は手順を作る。**
「何をどう操作して、何が起きたらこの指摘が成立するか」を番号付きで書く。実行はユーザー。**結果をもらえたら【検証済み】に昇格して投稿に加える**ので、報告時にその旨を伝える。

**【規約】は検証不要。** 引用した行がそのまま根拠になる。

## A-5. 文面を書く

1 コメントは **タグ + 3 要素 + 最大 5 行**。コードブロックは多くて 1 つ。長いと読み飛ばされ、読み飛ばされた指摘は直らない。

言語は PR の説明・既存コメントに合わせる (日本語のリポジトリなら日本語)。

**【不具合】** — 何が起きるか / どう確かめたか / 直し方:

```
【不具合】options 未指定で呼ぶと落ちる

createClient() を引数なしで呼ぶ経路があり、options.retry で TypeError になります。
テストを書いて実行し、実際に落ちることを確認しました。
`options?.retry` で回避できます。
```

**【規約】** — どの規約か / 現状との差分:

```
【規約】docs/rules/error-handling.md:42

「API 呼び出しの失敗は共通ハンドラに委譲する」
この catch で個別に握りつぶしています。
```

**【確認】** (ユーザーが投稿を選んだ場合のみ) — 何が決まっていないか / 問い:

```
【確認】上限を超えたときの扱いが決まっていないように見えます

件数が上限を超えた場合の分岐がなく、現状は黙って切り捨てられます。
意図した挙動でしょうか。
```

断定せず問いの形にする。仕様の判断は実装者の側にあり、こちらが決めることではない。

書けたら JSON にまとめる (`line` は **新しいファイル側の行番号**):

```json
[
  {"path": "src/app/foo.ts", "line": 88, "body": "【不具合】..."},
  {"path": "src/app/bar.ts", "line": 42, "body": "【規約】..."}
]
```

## A-6. 投稿する (確認不要)

```bash
bash ${CLAUDE_PLUGIN_ROOT}/skills/pr-review/scripts/post-pending-review.sh <PR番号|URL> <comments.json>
```

pending review は本人にしか見えないので、ここは確認を取らずに投稿してよい。ユーザーは GitHub 上でコードと並べて精査する。

| exit | 意味 |
| --- | --- |
| 0 | 投稿成功。`invalid` に除外分が入る |
| 5 | 投稿可能なコメントが 0 件 (全件が diff 外の行) |
| 6 | 既に未 submit の pending review がある。破棄を促して終了 |

スクリプトは投稿前に diff と行番号を突き合わせる。GitHub は diff に無い行へのコメントを 422 で弾き、**1 件でも不正だと全件落ちる**ため、除外して投稿する。`invalid` が出たら行番号を取り直して 2 回目を投げるか、その指摘を落とすか判断する。

2 回目以降 (行番号の取り直し、A-8 で選ばれた【確認】、実機確認後の追加) は、最初の出力の `review_id` を `--append <review_id>` で渡して同じ pending に追記する。ID が一致しない pending はユーザーが手で書いたドラフトとみなし、exit 6 で止まる。

レビュー本文 (全体コメント) は **空のままにする**。相手に一番強く届く部分なので、submit 時にユーザーが自分の言葉で書く。

## A-7. 引き継ぎメモを残す

修正確認 (フェーズB) は数日後の別セッションになることが多い。そのとき PR の理解や指摘の根拠を最初から作り直すと、トークンの大半がそこに消える。フェーズB に要るのは **何を・なぜ指摘し・どう確かめ・どうなれば閉じるか** だけなので、それだけを `fetch-pr-context.sh` の `review_memo.path` に書き残す。ディレクトリが無ければ作る。

```markdown
# PR #<N> <title>
<url> / レビュー時点: <head_oid 先頭7桁> / <日付>

## 変更の要点
<3〜5行。何をなぜ変える PR か>

## 投稿した指摘
### 1. 【不具合】foo.ts:88 options 未指定で TypeError
- 根拠: createClient() を引数なしで呼ぶ経路がある (bar.ts:20)
- 検証: テストで再現
  (テスト本文をそのまま貼る。ファイルは削除済みなのでここにしか残らない)
- 閉じる条件: options 未指定でも落ちない (上のテストが通る)

### 2. 【規約】bar.ts:42 共通ハンドラを通っていない
- 根拠: docs/rules/error-handling.md:42「API 呼び出しの失敗は共通ハンドラに委譲する」
- 閉じる条件: catch が共通ハンドラに委譲される

## 仕様・設計の確認事項 (未投稿)
- [妥当性] 失敗時の自動リトライで二重実行にならないか — api.ts:88

## 投稿しなかった指摘
- baz.ts:20 型定義上 null にならない (不成立)
- qux.ts:142 実機確認待ち: ① 一覧を開く ② 絞り込みを変更 ③ 表示が崩れるか
```

**閉じる条件**が一番大事。フェーズB の ✅ / ⚠ 判定がこれで客観的になる。**投稿しなかった指摘**は、再レビューで同じものを蒸し返さないために残す (1 行ずつでよい)。

書かないもの: 探索の経路、code-review や Agent の生出力、試して外れた仮説の過程。メモは数 KB に収める。長いメモは読み直すコストが高く、残す意味が薄れる。

A-8 の後に【確認】を pending に追加したり、実機確認の結果を受けて投稿を足したりしたら、メモも同じ内容に更新する。

## A-8. 報告する

ターミナルにはこれだけ出す:

```
## PR #<N> <title>
<url>/files
(--explain 指定時) 解説: <Artifact URL>

【投稿】不具合 <n> / 規約 <n>
| # | 分類 | 場所 | 一言 |
|---|------|------|------|
| 1 | 不具合 | foo.ts:88 | options 未指定で TypeError |
| 2 | 規約 | bar.ts:42 | error-handling.md:42 に反する |

【仕様・設計の確認事項】<n>件 (未投稿)
  1. [妥当性] 失敗時に自動リトライ3回 — api.ts:88
     副作用のある操作で二重実行にならないかが、コード側では決まらない
     確認先: 冪等性がサーバ側で担保されているか、実装者に確認
  2. [要件担保] 権限なしユーザーへの非表示 — view.ts:42
     説明に要件はあるが、この分岐だけで全経路が閉じているか読み切れない
     確認先: 他の入口 (直リンク・共有URL) からの到達可否
  3. [エッジ] 0件時の表示が仕様にもコードにも現れない — list.ts:30
     空配列で何が出るかが差分から読み取れない
     確認先: 既存画面の空表示の揃え方、仕様として決まっているか
  その他: [アーキ] 状態を component が直接持っている (store.ts:12)
          [エッジ] 上限超過時に黙って切り捨て (foo.ts:120)
  ※ 仕様書リンクは参照不可のため、[要件担保] は PR の説明の範囲で判定
  → 指摘として上げたいものがあれば番号で指定してください (pending に追加します)
  → 「その他」を詳しく見たい場合も番号で指定してください

【検証したが起きなかった】<n>件
  baz.ts:20  型定義上 null にならない

【検証手段なし — 実機確認候補】<n>件
  qux.ts:142  ① 一覧を開く ② 絞り込みを変更 ③ 表示が崩れるか
              → 結果をもらえれば投稿に加えます

【規約にない好み】<n>件 (命名・分割など)
【重複で除外】<n>件 (別のレビュアーが同じ箇所を指摘済み)

→ GitHub で確認して submit してください
→ `/check-review-validity <N>` で submit 前の最終チェックもできます
→ 引き継ぎメモ: <review_memo.path> (修正後は新しいセッションで `/pr-review <N>` を実行すればメモから始めます)
```

【仕様・設計の確認事項】は **詳細 3 件 + その他 1 行 × 最大 5 件**。迷ったら「実装者に聞かないと決まらないか」で切る。

検証テストを書いた場合は、その本文も添える (ファイルは削除済みなので、ここにしか残らない)。

最後に、Step 3 でブランチを切り替えていたら元のブランチに戻すか聞く。
