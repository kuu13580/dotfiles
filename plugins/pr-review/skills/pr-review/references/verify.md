# フェーズB: 修正を確認して閉じる

自分が出した指摘が潰れているかを確認し、Resolve して、残りがなければ Approve する。

ここでの失敗は 2 方向ある。直っていないのに Resolve すると指摘が消えるし、直っているのに確認を渋ると相手を待たせる。**コードを読んで確定させる**のが仕事で、「たぶん直った」で閉じない。

## B-1. スレッドと差分を取る

```bash
bash ${CLAUDE_PLUGIN_ROOT}/skills/pr-review/scripts/fetch-review-threads.sh <PR番号|URL>
```

| exit | 意味 |
| --- | --- |
| 0 | JSON 出力 |
| 1 | エラー |
| 3 | 自分が立てたスレッドが 1 件もない (フェーズA に回すか確認する) |

- `my_threads`: 自分が起点のスレッド。`replies` に実装者の返答が入る
- `my_last_review.commit`: 前回レビュー時点の commit。ここから `head_oid` までが今回見る範囲
- `new_commits`: 前回レビュー以降の commit
- `review_memo`: フェーズA が残した引き継ぎメモ

**`review_memo.exists: true` なら最初にメモを読む。** PR の要点・各指摘の根拠・検証に使ったテスト・閉じる条件が入っているので、PR を読み直して理解を作り直す必要はない。コードは差分と、判定に要る箇所だけ読めばよい。

ただし **正は GitHub のスレッド側**。ユーザーは submit 前に pending を編集・削除しているので、メモと食い違うことがある:

- メモにあるがスレッドが無い → ユーザーが削除した指摘。扱わない
- スレッドにあるがメモに無い → ユーザーが手で足した指摘。スレッド本文だけで判定する
- 両方にあるが文面が違う → スレッドの文面を正とし、メモの根拠と閉じる条件は参考にする

メモが無い (別の端末でレビューした、手で書いたレビュー等) ときは、従来どおりスレッドと差分から判定する。

Step 3 で手元の HEAD は PR の head に揃っている (fork の PR も `gh pr checkout` 経由なので同じ):

```bash
git diff <my_last_review.commit>..<head_oid>
```

`review_commit_found: false` はレビュー時点の commit が履歴に無い (force push 等) ということ。`new_commits` は直近の全件になり、上の diff も取れないことがある。その場合は base との全体差分で判定し、範囲を絞れなかったことを報告に書く。

## B-2. 各スレッドの対応を確認する

`is_resolved: false` のスレッドを 1 件ずつ見る。判定材料は **今のコード** と **差分** と **実装者の返信**、メモがあれば **閉じる条件**。閉じる条件を満たしているかで ✅ / ⚠ を決めると、判定がぶれない。

| 判定 | 条件 |
| --- | --- |
| ✅ 対応済 | 指摘した問題が現在のコードで成立しなくなっている |
| ⚠ 不十分 | 直ってはいるが別の経路が残る / 直し方が新しい問題を生んでいる |
| ❌ 未対応 | コードが変わっていない (返信だけで済まされている場合を含む) |
| 💬 議論中 | 実装者が「意図的」「別 PR で対応」と返しており、こちらの判断が要る |

【確認】のスレッドは問いなので、上の表ではなく返信で判定する。返信だけで閉じるのが正常で、コードが変わっていないことを ❌ にしない:

| 判定 | 条件 |
| --- | --- |
| 💬 回答あり | 実装者が答えている。回答を 1 行に要約し、Resolve するかはユーザーが決める |
| ⏳ 未回答 | 返信がない |

回答から修正が必要と分かり、実装者がコードを変えた場合だけ、上の表 (✅ / ⚠ / ❌) で判定する。

✅ の根拠は **commit か行番号で示す**。「対応されたようです」ではなく「`abc1234` で `?.` が入り、null 経路が閉じた」と書く。

指摘がテストで再現できたものだった場合は、**同じテストをもう一度書いて通ることを確認する**。メモにテスト本文があればそれを使う。書いたファイルは確認後に削除する (フェーズA と同じ扱い)。

## B-3. 追加 commit を再レビューする

修正のついでに別の問題が入ることは珍しくないので、`my_last_review.commit..head_oid` の差分にだけ、フェーズA と同じ基準を当てる。

- 洗い出しは `/code-review <level> <PR番号>` か、差分が小さければ直接読む
- **検証できたものだけ**を新規指摘とする (フェーズA と同じ)
- 分類も同じ (【不具合】/【規約】、規約は引用必須)
- 修正で仕様・設計として引っかかる点が出た場合は、フェーズA と同じく重要度を付け、critical / major は `【確認・要判断/<重要度>】` の目印付きで pending に置く (diff 外と minor はレポートのみ)
- メモの「投稿しなかった指摘」と「仕様・設計の確認事項」に既にあるものは新規として出さない。前回ユーザーが投稿しないと判断したものを蒸し返すことになる

PR 全体を再レビューし直さない。前回落とした指摘がぶり返して、実装者は「前回は何も言わなかったのに」となる。

## B-4. 報告して、承認をもらってから実行する

まず表で出す:

```
## PR #<N> <title>
前回レビュー: <submitted_at> / 以降 <n> commit

| # | 判定 | 場所 | 根拠 |
|---|------|------|------|
| 1 | ✅ 対応済 | `src/app/store.ts:88` | abc1234 で ?. が入り null 経路が閉じた |
| 2 | ⚠ 不十分 | `src/app/view.ts:42` | undefined 側の経路が残る |
| 3 | ❌ 未対応 | `src/app/api.ts:15` | 該当行に変更なし |

【追加 commit の再レビュー】新規 <n> 件
  【不具合】`src/app/nav.ts:30`  null ガードの条件が逆 (テストで再現済み)
```

場所はフェーズA と同じくリポジトリ相対の `path:line` で書く。

そのうえで、**1 つずつ承認を取る**。相手に届くものを勝手に送らないのがこのスキルの前提:

**(1) Resolve** — ✅ のものと、【確認】の 💬 回答ありのうちユーザーが回答に納得したものを挙げて確認する。

```bash
bash ${CLAUDE_PLUGIN_ROOT}/skills/pr-review/scripts/resolve-threads.sh <threadId> <threadId> ...
```

**(2) 返信** — ⚠ / ❌ / 💬 に返す文面をドラフトとして見せ、承認されたら送る。

```bash
bash ${CLAUDE_PLUGIN_ROOT}/skills/pr-review/scripts/reply-thread.sh <PR番号|URL> <reply_to_comment_id> <本文ファイル>
```

文面は「何が残っているか」と「どうなれば閉じられるか」の 2 点。責める書き方をしない。直し方が難しそうなら代替案を 1 つ添えると往復が減る。

**(3) 新規指摘** — B-3 で出たものは `post-pending-review.sh` で pending に積む (フェーズA の A-6 と同じ)。pending が残っている状態では Approve しない。

**(4) Approve** — 全スレッドが Resolve 済みで、新規指摘も pending も残っていないときだけ提案する。

```bash
gh pr review <N> --repo <repo> --approve --body "<ユーザーが承認した文面>"
```

`--body` を付けるなら文面も承認を取る。空でよければ `--body` ごと省く。

閉じきれないものが残る場合は Approve せず、「N 件残っています」と伝えて終わる。判断を急がせない。

## B-5. メモを更新する

修正確認は 1 往復で終わらないことがある。次の往復を安く始められるよう、終わる前に `review_memo.path` を今の状態に書き換える (メモが無かった場合は、フェーズA の A-7 の形式で新しく作る):

- 各指摘の判定 (✅ Resolve 済み / ⚠ / ❌ / 💬 / 【確認】の 💬 回答あり・⏳ 未回答) と、残っているものの閉じる条件
- B-3 で積んだ新規指摘 (根拠・検証・閉じる条件)
- 確認時点の commit を `head_oid` に更新

Resolve 済みの指摘は 1 行に畳む。次の往復で読み直す必要はない。

**Approve まで済んだら、メモを削除する。** 役目を終えたメモが残ると、Approve 後に commit が積まれて再レビューするとき、決着済みの古い判断を読み込んでしまう。削除したことは報告に 1 行添える。スキル外で Approve / マージされた場合は、次回実行時の Step 0 が削除する。
