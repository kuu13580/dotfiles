情報の見せ方と部品 layout.md

読む場面: どの画面でも

必須機能=一覧比較

一覧の各項目は、行や位置ごとの役割を全項目でそろえる

同じ種類の情報が同じ位置にあれば、縦に目を走らせるだけで比べられる。

必須既存のUI部品があるとき

生のHTML要素などで独自に作らずプロダクトの既存UI部品を使い、ない部品を仮に作るときも既存の見た目に合わせる

既存部品なら見た目も挙動(フォーカス・無効状態)もそろい、仮の部品も差し替えやすい。

必須条件なし

ボタンの色を画面ごとに上書きせず、部品に用意された種類(主・副など)を使う

個別に色を変えると色が意味を失う(別の見た目が要れば共通部品への種類の追加を検討)。

推奨機能=一覧比較

一覧から詳細へ移すのは操作や経緯などにとどめ、比較に使う情報は一覧に残す

比較材料を詳細に移すと、1件ずつ開いて覚えながら見比べることになる。

推奨条件なし

同じデータでも、画面の役割(見る・編集する・判断する)に必要な情報に絞って出す

役割に合わない情報は判断の材料にならず、視線を散らすだけになる。

推奨概観のための表示(地図の印や補助表示など)

全体をざっと見るための表示では、生の数字より名前や濃淡・大きさで表し、正確な数は詳細や一覧で見せる

数字の羅列は読み取りの負荷が高い(数字そのもので比べる表や集計は除く)。

推奨条件なし

縦に並べて比べる数字には等幅数字を使う

桁の幅がそろうと、上下の値の大小を位置で読み取れる。

例 CSSなら font-variant-numeric: tabular-nums を使う。

推奨条件なし

特定の意味に割り当てた色は、その意味以外に使わない

色が1つの意味に対応していれば色だけで分かり、流用するとその手がかりが崩れる。

推奨条件なし

色で区別するカテゴリは少数に抑える

色が増えると見分けにくく、凡例を見ないと意味が分からなくなる。

推奨条件なし

余白だけでまとまりを示せないときは背景色、次に罫線や枠線の順に検討し、囲みを重ねたり入れ子を深くしたりしない

囲みや罫線の多用は内容より枠を目立たせ、操作できる要素との区別も曖昧にする。

例 セクションは見出しと余白で区切り、1件ごとに操作する項目だけをカードで囲む。

推奨条件なし

タスクに必要な情報は画面上に常に表示し、ホバーやヘルプアイコンの中に入れるのは必要なときに見る補足説明にとどめる

ツールチップは消えて見落とされやすく、タッチではホバーもできない。

推奨条件なし

すぐ判断してほしい場面では選択肢を絞り、選択肢が多いときは推奨のものを目立たせる

判断にかかる時間は選択肢の数と複雑さに応じて増える(ヒックの法則)。

推奨条件なし

補助的なテキストは本文より色を薄くしたりサイズを一段小さくしたりして弱め、文字色の濃淡の段階を増やしすぎない

濃淡とサイズの差で補足と一目で分かる(本文として読めるコントラストは保つ)。

数値 目安(Erik Kennedy): 二次テキストは本文より約2px小さくし、色は本文の約70%の濃さの灰色から試す / WCAG 2.2 SC 1.4.3 (AA): 文字のコントラスト比4.5:1以上

推奨条件なし

重要な情報は上部・左側に置き、主ボタンは副ボタンより下側・右側の操作の流れの終点に置く

視線はF型やZ型に流れ、終点に主ボタンがあれば迷わない(並び順はOSや既存の慣習を優先)。

推奨条件なし

関係の近い要素ほど近づけ、関係の薄い要素とは大きく離して、余白の大小でまとまりと階層を示す

近くの要素は同じグループと知覚され、線や囲みなしに余白の差だけでまとまりが伝わる。

例 ラベルと入力欄の間 < 項目の間 < セクションの間 の順に余白を広げる。

数値 目安: グループ間の余白はグループ内の2倍以上(Proper Sky)。フォームでは差を小さめに取る例もある(Carbon: 入力欄の間が24pxならセクション間は32px)

推奨条件なし

必要な情報は表示したままにするか次の画面に引き継ぎ、画面をまたいでユーザーに覚えておかせない

短期記憶は限られ、思い出すより見て分かるほうが負担が小さい。

推奨条件なし

使い方の説明は一括のチュートリアルにまとめず、該当する操作をする場面でその近くに出す

ユーザーは説明を読まずに使い始めるため、その場のヒントのほうが理解され記憶に残る。

推奨条件なし

画面の主役になる要素や操作を絞って最も強く見せ、ほかは控えめにしつつ見つけられる状態に保つ

同じくらい目立つ要素が並ぶと焦点が定まらず、強調を重ねすぎても気が散る。

推奨条件なし

最初に見せるのはよく使う重要な情報や選択肢に絞り、専門的・まれな機能や一部の人だけが要る情報は2段目に回す

大半の人が余計な複雑さを見ずに済み、初期表示に置くこと自体が重要度を伝える。

推奨条件なし

全員が見るべき内容は折りたたみやタブで隠さず、まず内容の整理・分割・見出しで解決できないか考える

隠した情報は見落とされやすい(素早さが要る日常の業務ツールでは折りたたみも有効)。

推奨条件なし

補足情報は普段は控えめに表示し、通常と違う値になったときだけ強調する

常に強調すると強調の意味が薄れ、例外のときだけ目立たせれば注意すべき情報が伝わる。

推奨条件なし

画面や部品は理想の状態だけでなく、空・少量・大量・読み込み中・エラーの各状態でも成り立つようにする

通信は遅れ使われ方も想定外になり、理想の量だけを想定すると端の状態で崩れる。

推奨状況の推測が確かなとき

文脈から利用者の状況が明らかなときは、明示的な操作を待たずに表示を適応させる

自動で合わせれば手間が減る(一時的な表示の変化にとどめ、ナビゲーションや操作の位置・順は変えない)。

例 読み取らせるコードを表示している間だけ画面を明るくする。

推奨条件なし

アイコンは対象(名詞)か結果の状態(形容詞)を図柄にし、処理(動詞)を表すアイコンには一般的なもの以外ラベルを添える

処理は絵にしにくく覚えないと分からないが、対象や状態の図柄は見て推測しやすい。

チェックリスト

  • 段階的開示で隠した機能への入口は見つけやすい位置に置き、開くと何が出るか予測できるラベルを付ける
  • 文字列の途中切れをなるべく避け、切り詰めるときは全文を見られる手段を用意する
  • 利用者が入力する文字列の長短や画面・文字サイズの両極端でも崩れないレイアウトにし、長すぎるときの扱いを決めておく
  • 横スクロールやスワイプで続きがある領域は、続きがあると分かる手がかりを見せる 横にスクロールする領域を作るとき
  • 段階的開示の階層を深くせず、さらに要るならまず機能を単純化するか、高度な機能をまとめて探せる場所に整理する
  • 外観(ライト・ダーク)をOSの設定に追従させ、アプリ独自の外観設定は必要な場合に限る
  • 同じ役割の要素は見た目をそろえ、役割の違う要素、特に押せない要素をボタンやリンクに似せない

操作 actions.md

読む場面: どの画面でも

必須カードを押せるようにするとき

カードを押せるようにするなら、カード全体を押せる範囲にし、押せることを見た目で示す

押せる範囲が広いほど狙いやすく、押せると見て分かれば迷わない。

推奨条件なし

主ボタンは画面で最も促したい操作に絞り、ほかの操作は副ボタンの見た目にする

主ボタンが並び立つと次の一手に迷う(カードなど独立した領域ごとに置くのは可)。

推奨条件なし

同じ目的の複数の手段はボタンを並べずに入口をまとめ、押したときに説明付きの選択肢として出す

ボタンを並べると画面が操作で埋まり違いも分からず、まとめれば選ぶときに説明を読める。

例 「＋追加」を押すと「ファイルから取り込む」「手入力する」が説明付きで出る。

推奨機能=一括操作

複数件をまとめて扱う場面では、1件ずつの確定だけにせず、全選択やまとめて確定などの一括操作を用意する

1件ずつ確定させると手数が増え、どこまで済んだかも追いにくい。

推奨削除や除外を確定する前の段階があるとき

確定前に外した・削除予定にした項目は見た目で状態を示し、同じ場所で元に戻せるようにする

外したと見て分かれば確定前に見直せ、その場で戻せれば誤操作を恐れずに外せる。

例 外したカードは点線の枠・薄い色・取り消し線にし、ボタンを「戻す」に変える。

推奨画面遷移の直後やユーザーの操作の直後

移動そのものが目的でない限り、画面遷移や操作の直後に、その副作用として表示位置をスクロール・移動させない

見ていた場所や操作した場所から急に動かされると、見失って何が起きたかも分からない。

例 移動が目的の例: 戻ったときの位置の復元、送信エラー時の誤った欄へのフォーカス。

推奨一組の選択肢としてボタンを並べるとき

一組として並ぶ選択肢のボタンは大きさを揃え、推奨する方は大きさではなく強調度で区別する

同じ大きさなら一組と伝わる(作用範囲や役割が違うボタン同士は変えてよい)。

推奨条件なし

使えない操作を見せるか隠すかは、そのユーザーがいずれ使えるようになるかで決める

いずれ使えるものは見えていれば学べ、決して使えないものを見せても混乱させるだけ。

例 前提が未達の操作は無効で見せ、権限上使えない管理者向けの操作は出さない。

推奨障害などで一時的に機能しないとき

障害など一時的に機能しないボタンは、消しても混乱しないなら消し、消すと迷わせるなら理由が分かる状態で残す

説明なく消すと削除されたかと疑わせ、説明のない無効表示では理由が伝わらない。

推奨条件なし

操作の対象を先に選び、その後に操作を選ぶ順にし、ナビゲーションもタスク名ではなく対象の名前で構成する

タスクを先に選ぶとモードになり中断に手間がかかる(たまに使う手続き型の作業は例外もある)。

推奨条件なし

ユーザーがとれる操作が1つしかないなら、ユーザーにさせずにシステムが行う

1択の操作をさせても得られる情報はなく、無駄な手間になる。

例 選択肢が1つしかないプルダウンは出さず、その値を選んだ状態にする。

推奨条件なし

確定ボタンを無効にするのは選ぶだけの短いダイアログに限り、却下の操作は常に押せるようにする

却下はいつでもできるべきで、選ぶだけのダイアログなら足りないものは見れば分かる。

推奨条件なし

特定の範囲に作用する操作はその範囲のすぐ近くに置き、配置から作用範囲が分かるようにする

配置から作用範囲を予測できる(狭い幅・タッチでは画面全体の主な操作を下部に置いてよい)。

例 一覧の検索欄は一覧の直上、ページ送りは直下、全体の検索はそれより上に置く。

推奨条件なし

誤操作を確認で防ぐより元に戻せるようにすることを優先し、確認は取り消せない・金銭が絡むなど影響の大きい操作に限る

確認が多いと読まずに承認する癖がつく(繰り返す確認は止められるように、取り消せない操作は除く)。

例 削除はゴミ箱へ移すだけにして「元に戻す」を出し、完全な削除だけ確認する。

推奨条件なし

プラットフォームや他サービスの慣習に合わせ、定番の操作や表示で目新しさを出さない

ユーザーは他のプロダクトで期待を作っており、慣習との違いは学び直しを強いる。

推奨利用頻度=日常

日常的に使うツールでは、初心者の邪魔にならない形で熟練者向けの近道を用意する

同じ作業を複数の方法で完了できれば、初心者と熟練者の両方に対応できる。

推奨条件なし

危険な操作は頻繁に押される操作から離すか区切って置き、見た目の優先度も下げる

ミスタップは必ず起きるので、誤操作の代償を小さくする。

推奨入力手段=キーボード独自のキーボードショートカットを作るとき

独自ショートカットは修飾キー付きを基本にし、単一文字キーのものは無効化・再割り当て・フォーカス中のみ有効のいずれかにでき、少数ならUI要素のそばに小さく示し、多数ならヘルプページを用意する

単一の文字キーは音声入力や打ち間違いで誤って発動しやすく、示さないと気づかれない。

数値 WCAG 2.2 SC 2.1.4 Character Key Shortcuts (A)

チェックリスト

  • ユーザーが扱う対象ごとに作成・閲覧・更新・削除の手段を抜かさず用意し、使う頻度に応じて目立たせ方を変える

フィードバック feedback.md

読む場面: どの画面でも

必須条件なし

権限・資格・容量・サービス障害など入力に起因しない問題は入力欄のエラーにせず状況と次の手を伝え、権限がないと事前に分かるなら入力前に説明する

入力欄のエラーは直せる検証エラー用で、サービス側の問題を入力のせいに見せてしまう。

推奨条件なし

空状態は初回・全件を片付けた後・検索や絞り込みの0件・エラーを区別し、それぞれに合った説明と対処を示す

初回は機能の価値、検索0件は条件の変え方、エラーは原因と解決策と、伝えることが違う。

推奨条件なし

所要時間が分かる処理では完了率の表示を使い、途中で分かったら同じ位置・同じ系統の部品のまま不確定表示から切り替える

何%か分かれば、待つか、後でやり直すか、中止するかを判断できる。

推奨条件なし

完了率の表示は工程の重みを所要時間に合わせてできるだけ一定の速さで進め、序盤だけ急に進んで止まる見せ方をしない

進む速さから残り時間を見積もるため、途中でペースが落ちると不満が大きくなる。

推奨条件なし

同じ種類の処理の進捗表示はサービス全体・部品の中で形式と位置を統一し、途中で別の種類の表示に切り替えない

一貫していれば状態を学べて確実に見つかる(同じ位置・部品内での完了率への切り替えは可)。

推奨条件なし

操作の結果は、操作した場所やユーザーが見ている場所の近くで返す

注意の外のフィードバックは見落とされ重複操作を招く(ページ全体の結果は上部でよい)。

推奨条件なし

待ち時間の長さで表示を使い分け、ごく短ければ何も出さず、長ければ進み具合を示し、非常に長いなら他の作業を続けられるようにする

一瞬の表示はちらついて遅く感じさせ、長い処理に不確定表示だけだと止まったか分からない。

数値 目安(NN/g): 1秒未満は表示なし、約2〜10秒はループ表示、10秒以上は完了率表示 / Material Design 3: 200ms未満は表示なし、200ms〜5秒はローディングインジケーター、5秒超はプログレスインジケーター

推奨条件なし

読み込み表示は範囲に合わせて選び、ページや広い領域ではレイアウトを先に見せ、ボタンや入力欄など単一の部品の形は模さない

レイアウトを先に見せると待ちが短く感じ、単一の部品はスピナーで足りる。

推奨条件なし

読み込みや処理の間も画面全体を止めずに他の操作を続けられるようにし、全体を止めるのは操作を止める必要がある場合に限る

待つ間に他の作業を進められ、不要なブロックは作業を妨げる。

推奨失敗がまれで失敗時に元の状態へ戻せる操作お気に入り・既読・並べ替えのようにユーザーが入力した内容を伴わない操作

成功の見込みが高く元に戻せる、入力を伴わない操作は、サーバーの応答を待たずに結果を表示し、失敗したら伝えて元に戻す

待ちをなくして速く感じさせつつ失敗時の食い違いも解消できる(入力を伴うものは完了を待つ)。

推奨条件なし

エラー(既に起きた問題)と警告(起こりうる問題)を文言と見た目で区別し、エラーを和らげるために警告の見た目を使わない

エラーは行動の後、警告は問題の前に出すもので、起きたかが伝わらないと対処を誤る。

推奨条件なし

動きや音だけで重要な情報やフィードバックを伝えず、テキストや触覚など別の手段でも伝える

消音中・画面を見ていない・読み上げ利用・アニメーション無効の人には動きや音が届かない。

推奨条件なし

処理の開始だけでなく完了と失敗も伝え、失敗を握りつぶさず、応答がなければ一定時間で打ち切り、何が起きたかと再試行などの次の手を示す

推奨条件なし

読み込み中や取得に失敗したときに空の表示を出さず、0件は取得が完了したうえで0件と分かる形で伝える

チェックリスト

  • ユーザーが気にしない、または行動を変えようがない問題をエラーとして表示しない
  • ある画面で編集した内容は、同じ対象を表示しているほかの箇所にもすぐ反映させる
  • クリック・タップ・キー入力には、処理の完了を待たずにすぐ押下状態などの視覚的な反応を返す
  • 読み込み中も最終的な内容の場所と大きさを確保し、読み込みの完了や遅れて届く要素でレイアウトをずらさない
  • 処理中のボタンでは処理中であることを示しつつ、何を実行中か分かるラベルを消さない
  • 待ち時間の表示には「読み込み中」だけで済ませず、何を待っているかを具体的に添える

入力 form-flow.md

必須条件なし

推奨主要な入力欄が1つだけの画面

主要な入力欄が1つだけの画面では、ポインタ操作の端末なら開いた時点でフォーカスし、タッチ端末では自動でフォーカスしない

デスクトップではすぐ入力でき、タッチではキーボードが画面を覆いレイアウトが動く。

推奨プラットフォーム=Web

Enterキーの挙動は入力の種類の慣習に合わせ、1行の入力ではEnterで送信、複数行の入力ではEnterで改行できるようにする

複数行でEnterを送信にすると改行できず誤送信を招く(チャット欄はEnter送信・Shift+Enter改行でよい)。

例 1行の欄はform要素で囲んで標準の送信を使い、複数行の欄は⌘/Ctrl+Enterで送信する。

推奨プラットフォーム=Web

入力欄には目的に合ったautocomplete属性と意味のあるnameを付け、ブラウザやパスワードマネージャーの自動入力を働かせる

自動入力で手間とミスが減り、type属性だけでは欄の目的(本人のメールか他人のか)が分からない。

例 サインインのパスワード欄に autocomplete="current-password"、新規設定は "new-password"。

数値 WCAG 2.2 SC 1.3.5 (AA)

推奨プラットフォーム=Web

数値を入力する欄では数字用のキーボードを出し、ホイールで値が変わるなどの副作用がある数値専用の入力型を使わない

type="number" はスクロールで値が意図せず増減し、数字以外を入れても反応がない。

例 テキスト型の欄に inputmode="numeric"(小数なら "decimal")を付ける。

推奨プラットフォーム=Web入力手段=タッチ

画面上のキーボードが出たときに、入力欄や下部に固定したUIが隠れないようにする

既定ではキーボードは見えている領域だけを縮め、レイアウトは追従しない。

例 下部固定のパネルは Visual Viewport API で高さを測りキーボードの上に置く。

推奨プラットフォーム=Web

アニメーションでレイアウトの再計算や再描画を毎フレーム起こすプロパティを動かさず、移動・拡縮・透明度の変化で表現する

transform と opacity は合成だけで安価だが、レイアウト系は毎フレーム再配置しカクつく。

推奨プラットフォーム=Web

ホバーの見た目はホバーできる端末に限って適用し、どの端末でも機能する既定の見た目を先に用意する

タッチ端末では押した瞬間にホバー状態が出て貼り付き、誤ったフィードバックになる。

例 ホバーの強調を @media (hover: hover) の中に書く。

必須プラットフォーム=Webサーバー描画後にクライアントで動かす構成

サーバーで描画したページにスクリプトが動きを付けるときに、利用者が入力し始めた値やフォーカスを消さない

必須プラットフォーム=Web

フォーム内の送信以外のボタンが、押しただけでフォームを送信しないようにする
